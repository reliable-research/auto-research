## N2 — Motivation

**`motivations`:**

1. `motivation_text` [HYPOTHESIS]: "As coding agents are increasingly trusted to autonomously complete multi-step software-engineering tasks in real repositories, the project's test suite is typically the only automated acceptance gate a patch must clear — the dominant evaluation paradigm defines correctness solely as fail-to-pass test execution ([SWE-bench, OpenReview:VTF8yNQM66]), and even work that criticizes unit-test grading replaces it with end-to-end tests rather than structural checks ([SWE-Lancer, OpenReview:xZXhFg43EI]). Test suites are not designed to check architectural or design-level constraints (layering, acyclic dependencies, module boundaries), so accepted, test-passing patches can silently degrade architecture over many accumulated edits — a hidden, compounding maintainability risk that is currently invisible to teams relying on agentic coding pipelines." `evidence: [{type: "citation", text: "[SWE-bench, OpenReview:VTF8yNQM66]; [SWE-Lancer, OpenReview:xZXhFg43EI]", source: "inferred", location: null}]`
2. `motivation_text` [HYPOTHESIS]: "Architectural erosion and growth of complexity have historically been studied as slow, human-driven phenomena across long project histories — Lehman's laws posit that evolving software's complexity increases unless work is done to reduce it ([Lehman, 1980]), and the erosion literature is built almost entirely on human-authored change histories ([Li et al., 2022]; [Sas et al., 2021]). Agentic, high-throughput automated editing changes the cadence and possibly the mechanism of erosion (e.g., compounding context drift over long agent horizons is already documented in other agentic settings, [SimpleTIR, OpenReview:EplNy91Xqh]), so prior human-centric erosion findings cannot be assumed to transfer, making a dedicated longitudinal measurement worthwhile." `evidence: [{type: "citation", text: "[Lehman, 1980]; [Li et al., 2022]; [Sas et al., 2021]; [SimpleTIR, OpenReview:EplNy91Xqh]", source: "inferred", location: null}]`

## N6 — Methodology

**`overview`** [HYPOTHESIS]: "A two-stage longitudinal measurement design. **Stage 1 (pilot = the seed's minimal experiment):** on one repository with dense SWE-bench Verified coverage (e.g., django/django), build one chronologically ordered sequence of ~20 issue-derived tasks; run one coding agent (e.g., OpenHands + a pinned frontier model) serially on a persistent checkout, accepting each patch iff it passes the task's fail-to-pass tests plus the regression suite; after every accepted patch, run the static-analysis pipeline and plot per-step metric drift against the human-gold-patch control trajectory on the identical sequence. The pilot's only job is to establish that (a) serial task sequences are constructible (later tasks apply after earlier agent patches) and (b) drift, if any, is measurable above noise. **Stage 2 (scale-up):** a factorial design — 3 repositories × 3 agents (agent scaffold × backbone) × 2 task orderings × 3 seeds — each trajectory ~20 steps, all against per-repo human-gold control arms and a random-order control; erosion-rate statistics from a mixed-effects longitudinal model are then regressed on candidate factors, and a patch-level mechanism profiler links drift to concrete edit behaviors (cross-layer import additions, duplication, edit locality)."

**`key_components`:**

- `id`: "M1" `name`: "Serial Task-Sequence Harness" `text` [HYPOTHESIS]: "Builds executable serial sequences from SWE-bench Verified instances grouped by repository and ordered by issue creation date (django, sympy, astropy have the densest instance coverage); runs each task in the benchmark's Docker environment but against the *current* (agent-evolved) checkout instead of the instance's original base commit, rebasing each task's fail-to-pass tests onto that checkout and discarding tasks whose tests no longer apply cleanly (logged as sequence attrition). Commits a patch iff the acceptance gate (M5) passes; instrument = the SWE-bench harness plus a sequence controller; granularity = one commit per accepted task."
- `id`: "M2" `name`: "Architecture Metric Extractor" `text` [HYPOTHESIS]: "A static-analysis pipeline run on the snapshot after every accepted patch (the study's ground truth per the seed's constraint): (a) module-level import graph via pydeps/grimp, cyclic-dependency count = number of modules inside strongly connected components of size > 1; (b) layering-violation count = imports violating per-repo import-linter contracts declared once from the project's documented package structure and frozen before any run; (c) architectural smells (cyclic dependency, hub-like dependency, unstable dependency) via an Arcan-style detector; (d) coupling/complexity: fan-in/fan-out, MacCormack propagation cost, radon cyclomatic complexity and maintainability index; (e) duplication % via jscpd. Granularity = per accepted step, reported at module and repo level."
- `id`: "M3" `name`: "Longitudinal Drift Model" `text` [HYPOTHESIS]: "Aggregates per-step readings into trajectories and estimates erosion rate two ways: (a) slope of each metric over step index from a mixed-effects linear model with trajectory-level random effects (autocorrelation-aware), and (b) a discrete-time survival analysis of time-to-first-new-architecture-violation per trajectory (censoring trajectories that never violate), directly adapting the survival framing of [Time-To-Inconsistency, OpenReview:88C7vSdn0t] from dialogue turns to accepted patches."
- `id`: "M4" `name`: "Counterfactual + Factorial Comparison Design" `text` [HYPOTHESIS]: "Three control/comparison arms on identical task sequences: (a) human-gold control — the actual PR gold patches applied in the same order (the counterfactual erosion rate); (b) ordering control — a second, permuted task order per repo; (c) agent contrast — 3 agent configurations (e.g., OpenHands+GPT-class, SWE-agent+Claude-class, Agentless+open-weight) × 3 seeds. Factor attribution comes from contrasts within this design, never from a single trajectory."
- `id`: "M5" `name`: "Architecture-Blind Test Gate" `text` [HYPOTHESIS]: "Acceptance oracle per task = the task's rebased fail-to-pass tests + the repository's pass-to-pass regression suite, exactly mirroring the [SWE-bench, OpenReview:VTF8yNQM66] correctness definition; deliberately excludes linters and all M2 checks, so 'passes tests yet erodes architecture' cases are isolated rather than masked. Rejected patches trigger up to k retries, then the task is skipped (logged), keeping the sequence architecture-uncontaminated."
- `id`: "M6" `name`: "Patch-Level Mechanism Profiler" `text` [HYPOTHESIS]: "For every accepted patch (agent and human arms), extracts a feature vector: LOC added/deleted, number of files/modules touched, new import edges and whether each crosses a declared layer boundary, duplication introduced (jscpd delta), and edit locality (graph distance between touched modules). These features are used to *explain* drift — regressing per-step metric deltas on patch features — supplying the 机制 (mechanism) half of the seed's label."
