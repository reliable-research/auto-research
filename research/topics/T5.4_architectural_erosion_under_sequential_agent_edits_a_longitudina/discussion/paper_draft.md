# Passing Every Test, Eroding the Architecture: Measuring Structural Drift under Sequential Coding-Agent Edits

> Assembled from the six confirmed stage outputs in `pipeline.md`, post-audit (`taste_audit.md`: 🟢), post-review (`review_2026-08.md`: concede-and-claim repositioning applied against SlopCodeBench and CodeThread, 2026-08-21). ## Abstract

Autonomous coding agents increasingly complete multi-step software-engineering work under a single automated acceptance signal: whether the patch passes the project's tests. We show this signal is blind by construction to the one property it cannot see — dependency direction, layering, and module-boundary structure — so a sequence of individually test-passing patches, applied serially to the same repository, could erode its architecture without the acceptance gate ever registering a problem. We measure this directly. Coding agents solve chronologically ordered task sequences drawn from real repositories on a single persistent checkout; patches are admitted only by test execution; six static-analysis metric families are recorded after every accepted step. A human-gold counterfactual arm solves the identical task sequence, isolating agent-attributable erosion from the structural growth any correct implementation would also require; a single-shot control arm separates whether accumulated history amplifies drift beyond the sum of independent per-patch damage. Patch-level features — cross-layer imports, duplication, edit locality — are regressed against the observed drift to attribute it to concrete mechanisms. We report which erosion regime dominates for current coding agents, whether it exceeds the human-authored counterfactual, and what predicts its rate.

## Introduction

Coding agents are no longer confined to single-file completions; they are routinely delegated multi-step software-engineering work — fixing an issue, then the next, then the next — against a real, evolving repository. In almost every deployment of this kind, one signal decides whether a given patch lands: does it pass the project's tests. That signal is cheap to compute, unambiguous, and already built into every continuous-integration pipeline, which is exactly why it has become the default acceptance gate for autonomous agents as much as for human contributors.

Yet a central property of this gate goes unexamined: a test suite is blind, by construction, to dependency direction, layering, and module-boundary structure. It can tell you that a function still returns the right value; it cannot tell you that reaching that value now requires an import that crosses a layer boundary the project was built to keep closed. A sequence of patches that each clear this gate individually could therefore still be walking the repository's architecture toward a worse state — rising cyclic dependencies, eroding layering, accumulating duplication — with no step of the acceptance process ever registering that anything went wrong. Whether this actually happens, and how badly, is not something a green test suite can answer on its own.

The closest prior work to this question sits on three sides of the gap being measured, and it is worth naming all three plainly. On the acceptance-protocol side, SWE-bench supplies the exact gate this paper adopts — patch correctness defined by fail-to-pass and regression test execution on real repository issues — but grades each instance independently from its own fixed base commit. On the classical measurement side, Sas et al.'s empirical study of architectural smells links source-code changes to the dynamics of cyclic and hub-like dependencies, but only across ordinary, human-authored open-source commit histories. And a recent wave of work has begun measuring degradation of agent-authored code directly: SlopCodeBench shows that agents iteratively extending their own solutions accumulate structural erosion and verbosity faster than open-source baselines, and CodeThread shows that downstream agents resolve fewer tasks when building on agent code than on human code. We concede the phenomenon-level headline to that work — that iterated agent editing degrades code structure is no longer an unmeasured conjecture. What remains unmeasured, and is this paper's estimand, is erosion of a real, mature repository's dependency architecture under a test-only gate, identified against a matched counterfactual: the human-authored gold patches for the identical, chronologically ordered task sequence, so that structural growth the tasks themselves require cancels out of the contrast and only the agent-attributable excess remains. SlopCodeBench's human comparison is a population of unrelated repositories, not the same tasks; CodeThread's outcome is downstream task resolution, not a per-step architectural trajectory. Neither can say whether a given agent, on a given real codebase, erodes layering and dependency structure faster than the humans who actually solved those very tasks — which is exactly the contrast this paper's instrument is built to compute.

Turning this into something measurable surfaces four distinct obstacles. First, because the acceptance gate carries no structural information whatsoever, any claim that a patch "passed yet eroded architecture" needs its own independent, out-of-band instrumentation of architectural state — otherwise the claim risks circularity with the very gate it is trying to look past. Second, not all structural growth is erosion: a feature that genuinely needs a new cross-module call would add exactly the same kind of coupling a human developer would also have to add, so raw metric worsening only becomes a meaningful claim once it is measured relative to what a correct implementation of the same tasks would have required anyway. Third, if erosion is real, it likely accumulates through many individually small violations across a long sequence — the kind of slow, compounding signal a single before-and-after snapshot would simply miss, and that naive statistics would either wash out as noise or falsely amplify through unaccounted step-to-step correlation. Fourth, knowing that erosion happens is not the same as knowing what to change about it — attributing a rate to specific agents, task types, or patch behaviors would normally call for a larger, more varied sample, but each additional condition here costs an entire serial, non-parallelizable trajectory, so attribution has to be extracted efficiently rather than assumed to come for free from scale.

Our approach turns each obstacle into a specific design choice. We keep the acceptance oracle deliberately restricted to test execution — confirmed, by a direct static scan of every task's test files, to contain no assertion that could see import structure at all — while an independent static-analysis pipeline records six architecture-metric families after every accepted step, so any measured change is provably a case the gate could not have seen. A human-gold counterfactual arm solves the identical, chronologically ordered task sequence under identical rules, so the structural growth any correct solution would need cancels out of the contrast, leaving only the agent-attributable excess. The resulting per-step metric series is modeled with trajectory-level random effects and an independent nonparametric trend test, so a slow compounding signal is judged against its own noise rather than against an arbitrary snapshot pair. And a deliberately small, contrastive factorial over agent configuration, task type, and ordering is combined with a per-patch feature profiler — cross-layer imports, duplication, edit locality — so that some attribution comes from features already collected within each trajectory, rather than requiring an ever-larger set of expensive new ones.

We evaluate this design on chronologically ordered task sequences drawn from real, densely-covered open-source repositories, contrasting agent-driven trajectories against a matched human-gold counterfactual and a single-shot, no-accumulated-history control, and reporting whichever erosion regime — decaying, persistent, or absent — the evidence actually supports.

In summary, we contribute:
- An operational definition of "architecture-blind" acceptance and a direct, falsifiable check of it: a static scan establishing that the dominant test-only acceptance gate for coding agents contains zero assertions capable of detecting the structural properties this paper measures.
- A counterfactual design that separates agent-attributable architectural erosion from the structural growth any correct implementation of the same task sequence would also require, rather than treating raw metric worsening as erosion by default.
- A longitudinal drift model, combining trajectory-level mixed effects with an independent nonparametric trend test and a survival-style time-to-first-violation analysis, purpose-built to detect a slow, compounding structural signal against ordinary step-to-step noise.
- A patch-level mechanism profile — cross-layer imports, duplication, edit locality — that attributes observed drift to concrete, checkable edit behaviors rather than leaving "erosion happens" as an unexplained aggregate finding.

## Problem Definition

**Formal setup.** Consider a repository with state s₀ and a chronologically ordered sequence of tasks T = (t₁, …, t_N) drawn from that repository's real development history. An editor policy π — a coding agent configuration, or the human-gold patch author — produces patch pᵢ = π(tᵢ, s_{i-1}) for each task in order, applied to one persistent checkout. A gate G(pᵢ, s_{i-1}, tᵢ) ∈ {0, 1} admits the patch iff tᵢ's designated fail-to-pass tests and the repository's regression suite both pass; the accepted state is sᵢ = s_{i-1} ⊕ pᵢ if G = 1, and sᵢ = s_{i-1} otherwise (after a bounded number of retries, the task is skipped and logged). After every accepted step, a metric vector Φ(s) records the repository's architectural state — cyclic-dependency count, layering-violation count against a frozen import contract, architectural-smell count, coupling/complexity measures, and duplication ratio. The object of study is the long-run behavior of {Φ(sᵢ)}: does it hold within a stable band, drift upward for a given arm π (within-arm erosion), and — if so — does the agent arm's drift exceed the human-gold arm's drift on the identical task sequence (agent-attributable erosion)? A parallel question asks which task, agent, and patch-level factors predict the rate of whichever drift is observed.

**Why this is hard.** The gate G is defined purely over test outcomes and carries no information about dependency structure, so nothing about G's own behavior can certify or refute a structural claim — architectural state has to be measured entirely out-of-band, and that measurement has to be shown, not assumed, to be independent of what the gate checks. Because a correct solution to a real task can legitimately require new coupling (a feature that needs a new cross-module call), a rising Φ is not automatically erosion: the quantity of interest is a difference against a matched counterfactual trajectory on the identical task sequence, not a raw within-arm trend. That trend, in turn, is realized through a long, individually noisy sequence of edits, so a genuine slow drift has to be separated from ordinary step-to-step variability using statistics built for autocorrelated, unevenly-sized increments rather than a two-point comparison. Finally, because each trajectory is a single persistent checkout whose steps depend on one another, the condition space that could explain a given drift rate — which agent, which task type, which ordering, how eroded the repository already was — cannot be explored by simply running more independent, cheaply parallelizable samples; each additional condition costs an entire new sequential run.

## Method Overview

At a conceptual level, this is a single longitudinal measurement pipeline with four cooperating parts. A restricted, provably structure-blind acceptance gate and an independent metric extractor turn a sequence of accepted patches into a per-step architectural time series; a human-gold counterfactual design turns that time series into a claim about what the agent, specifically, adds; a longitudinal drift model turns the resulting series into a rate and a verdict about whether real drift is present; and a patch-level mechanism profiler turns the same accepted patches into an explanation of what carries whatever drift is found.

The **architecture-blind acceptance and metric extraction** stage admits patches using test execution alone, having independently confirmed that the test files themselves contain no structural assertions, and records the six-metric architectural state after every admitted step. The **human-gold counterfactual design** runs the identical task sequence a second time through the original human-authored patches under the same rules, so that whatever structural growth a correct solution requires appears in both arms and only the excess is attributed to the agent. The **longitudinal drift model** fits the resulting per-step series with trajectory-level random effects, cross-checks the fit against an independent nonparametric trend test, and models time-to-first-new-violation as a censored survival process. The **attribution and mechanism profiling** stage extracts a small, per-patch feature vector — cross-layer import edges, duplication delta, edit locality — for every accepted patch in both arms, and combines it with a small, deliberately contrastive factorial over agent configuration, task type, and ordering, so that erosion rate can be explained by both condition and concrete edit behavior without requiring a larger sample than the study can afford.

## Methodology

### Architecture-Blind Acceptance and Metric Extraction

**Challenge.** The dominant acceptance signal for coding-agent patches is test execution, which carries no information about dependency direction, layering, or module boundaries — so any claim that a "passing" patch nonetheless changed the repository's structure needs its own, independently verified instrumentation, or it risks circularity with the very gate being studied.

**Insight.** Architecture-blindness does not have to be assumed; it can be checked directly, and once checked, any structural change measured after an accepted step is by construction a case the gate could not have seen.

**Method.** Each task's fail-to-pass tests and the repository's regression suite are the sole admission criterion for a patch; before any run, every task's test files are statically scanned for assertions referencing import structure, module boundaries, or layering, confirming the gate is structurally uninformative for the studied repositories. After every admitted patch, a static-analysis pipeline records: cyclic-dependency count (modules inside strongly connected components of the import graph), layering-violation count (against import contracts frozen from each repository's documented package structure before any run), an architectural-smell count, coupling and complexity measures (propagation cost, fan-in/fan-out, cyclomatic complexity, maintainability index), and a duplication ratio.

### Human-Gold Counterfactual Design

**Challenge.** Raw metric worsening conflates two different things: structural growth a correct solution to the task genuinely requires, and structural degradation specific to how the agent solved it — without separating them, any observed increase in complexity would be misread as erosion.

**Insight.** A benign, task-required structural change appears whether the task is solved by an agent or by the original developer; only a difference between the two arms, on the identical task sequence, isolates what the agent specifically adds.

**Method.** The original human-authored patches for the same chronologically ordered task sequence are applied under identical rebasing and attrition rules as the agent arm, producing a matched counterfactual trajectory. Agent-attributable erosion is defined as the excess of the agent arm's fixed-effect trend over the human-gold arm's trend, computed on the task intersection both arms actually complete. The same specification separates two claims from one fit: the human-gold arm's own trend (whether the task sequence itself requires structural growth) and the arm-interaction term (whether the agent adds erosion beyond that baseline) — one design, two distinct, separately falsifiable readouts.

### Longitudinal Drift Model

**Challenge.** If erosion is real, it plausibly accumulates through many small, individually unremarkable violations across a long sequence; a single before/after comparison would miss it, and treating each step as an independent observation would either wash out a true slow signal as noise or manufacture significance from unaccounted step-to-step correlation.

**Insight.** Modeling each trajectory's own variability explicitly — rather than pooling steps as if they were independent — is what lets a small, compounding signal survive contact with ordinary run-to-run noise.

**Method.** Each metric's per-step trajectory is fit with trajectory-level random slopes and intercepts, so a condition-level trend claim is evaluated net of pair-specific variability. Independently, a nonparametric monotone-trend test is applied per trajectory as a check that does not depend on the mixed-effects model's assumptions. A discrete-time survival model, adapted from turn-level hazard modeling of conversational degradation to accepted patches, estimates time-to-first-new-architecture-violation, retaining trajectories that never violate as censored observations rather than discarding them.

### Attribution and Mechanism Profiling

**Challenge.** Detecting that erosion happens does not explain what to change about it, but explaining it usually calls for more data — more agents, more task types, more orderings — while each additional condition here costs an entire new, non-parallelizable trajectory.

**Insight.** Some attribution signal can be extracted from the trajectories already run, rather than only from adding more of them: a per-patch feature vector supplies a cheaper, within-trajectory channel of explanation alongside a small, deliberately contrastive between-trajectory factorial.

**Method.** For every accepted patch in both arms, a feature vector records new cross-layer import edges (imports whose endpoints cross a frozen layer boundary), the change in duplicated-line ratio, and edit locality (the graph distance between modules touched by the patch). Per-step metric deltas are regressed on these features within trajectories to attribute drift to concrete edit behavior. Separately, a small factorial over agent configuration, task type, and task ordering, run across independently seeded trajectories, is regressed against trajectory-level erosion rate to attribute rate differences to condition-level factors, net of one another.

## Experiments

### Experimental Setup

**Datasets.** SWE-bench Verified, grouped by repository and ordered chronologically by issue creation date, restricted to the repositories with the densest instance coverage (django/django, sympy/sympy, astropy/astropy) — real, dateable development histories on Python codebases with declarable import-layer architectures, letting a serial task sequence be built on genuine history rather than a synthetic one. SWE-bench Lite is used secondarily, specifically to construct the second, permuted-order sequence the ordering-factor RQ (RQ6 below) needs when a given repository's Verified-instance density is too thin to support two independent chronological orderings on its own; without it, ordering would be tested confounded with repository choice.

**Baselines** (sanity-check comparators, not competitors to beat — this is a measurement study, and no research question here is framed as "our procedure beats baseline X"). The human-gold arm, identical to the agent arm in every respect except the patch author, is the necessary control for every agent-attributable-erosion claim. A single-shot control arm — the same agent and backbone, solving each task from its own original base commit with no accumulated agent history — is the necessary control for a different question: whether accumulated history amplifies erosion beyond what independent, non-sequential edits from the same agent would produce on their own. This contrast is reported alongside RQ2 below as a check on the sequence-specific reading of any observed excess erosion, rather than as its own separately numbered research question, since it supports the same headline hypothesis rather than testing a distinct one.

**Metrics.** The six architectural-metric families (cyclic dependencies, layering violations, architectural smells, propagation cost/fan-in/fan-out, complexity/maintainability, duplication ratio) and their per-trajectory trend estimates; the discrete-time hazard of first new violation; the patch-level feature vector (cross-layer imports, duplication delta, edit locality); and the resulting condition-level classification of drift as absent, within-arm-only, or agent-attributable.

**Research questions:**
1. RQ1 — Is the acceptance gate actually structurally uninformative, as the method assumes?
2. RQ2 — Does the agent arm's structural trend exceed the human-gold arm's trend on the identical task sequence?
3. RQ3 — Is within-arm drift alone, without the counterfactual contrast, sufficient evidence of agent-attributable erosion?
4. RQ4 — Do two independent statistical readings of trajectory drift agree with each other?
5. RQ5 — Are the three patch-level features load-bearing carriers of the observed drift?
6. RQ6 — Which conditions predict erosion rate, net of one another?

#### RQ1: Is the acceptance gate actually structurally uninformative, as the method assumes?

**Setup.** For every task's designated test files across the three primary repositories, statically scan for assertions that reference import structure, module membership, or declared layering, prior to any experimental run.

**Expected outcome.** Zero qualifying assertions are found across all scanned test files, confirming the acceptance signal is structurally uninformative by construction rather than merely in the studied instances.

**Falsification condition.** Refuted if any repository's test files contain assertions that do reference import-graph or layering structure — in which case the "architecture-blind" premise must be scoped to exclude those tasks, or the gate's blindness re-argued on the remaining subset.

**Hypothesis (plain language).** The dominant test-only acceptance signal for coding-agent patches carries no structural information at all, not just weak or incomplete structural information.

#### RQ2: Does the agent arm's structural trend exceed the human-gold arm's trend on the identical task sequence?

**Setup.** Pilot stage: 1 repository (django) × 1 agent configuration × 1 ordering × 3 seeds, ~20 tasks, contrasted against the matched human-gold arm on the same sequence; go/no-go gated on a walking-skeleton feasibility check (a pre-registered minimum of 60% of tasks surviving test-rebasing onto the agent-evolved checkout — below which the design falls back to a curated synthetic task sequence on one mid-size layered application, trading task realism for guaranteed sequence validity, with attrition reported as a first-class outcome either way — plus a bitwise-deterministic metric re-run, and a power projection from the pilot's observed step-to-step metric variance requiring ≥ 0.8 projected power to detect the pre-registered effect-size floor before any scale-up spend). Scale-up: 3 repositories × 3 agent configurations × 2 orderings × 3 seeds (54 agent trajectories, ~20 steps each) contrasted against per-repository human-gold and single-shot control arms. Mixed-effects specification: metric ~ step × arm + task-level covariates + (step | repository:seed), with the step × arm interaction as the estimand of interest, Holm-corrected across the primary metric family.

**Expected outcome.** For at least two of the three primary structural metrics (cyclic dependencies, layering violations, duplication), the step × arm interaction is positive and clears the pre-registered effect-size floor (Cliff's δ ≥ 0.33 on per-trajectory slope pairs) on the shared task-intersection contrast, indicating agent-attributable excess erosion beyond what the human-gold arm's own trend already accounts for.

**Falsification condition.** Refuted if the interaction term is non-significant, or favors the agent arm, for all three primary metrics after Holm correction — i.e., agent-authored erosion is statistically indistinguishable from, or better than, the human-gold counterfactual on the same task sequence. The single-shot control contrast (Setup, above) is reported alongside this result: if excess erosion holds against the human-gold arm but the agent's serial and single-shot cumulative drift are statistically indistinguishable, the finding is reframed as "erosion is per-patch additive, not sequence-amplified," which changes the practical implication from trajectory-level monitoring to per-patch gating.

**Metrics.** Per-metric step × arm interaction estimate and confidence interval; per-trajectory Mann-Kendall trend statistic as a robustness cross-check; seed-level dispersion.

#### RQ3: Is within-arm drift alone, without the counterfactual contrast, sufficient evidence of agent-attributable erosion?

**Setup.** Among all studied trajectory pairs (agent arm and its matched human-gold counterfactual on the same task sequence), identify pairs where both arms show a statistically significant within-arm trend, and compare the two arms' trend magnitudes directly.

**Expected outcome.** At least one qualifying trajectory pair shows within-arm drift present in both the agent and human-gold arms at statistically indistinguishable rates, demonstrating that within-arm drift by itself does not imply agent-attributable erosion.

**Falsification condition.** Refuted if, in every trajectory pair showing within-arm drift in the human-gold arm, the agent arm's rate is always distinguishably different (never statistically indistinguishable) — which would suggest within-arm drift and the counterfactual contrast are redundant rather than the counterfactual doing genuinely separate work.

**Hypothesis (plain language).** A trajectory can look like it is eroding on its own terms while carrying no agent-specific signal at all, which is exactly why the counterfactual contrast, not the within-arm trend, is the paper's central claim.

**Metrics.** Count and identity of qualifying trajectory pairs; per-pair trend-magnitude difference and its confidence interval.

#### RQ4: Do two independent statistical readings of trajectory drift agree with each other?

**Setup.** Among trajectories flagged by either the mixed-effects slope estimate or the per-trajectory Mann-Kendall test as showing any drift, compare the sign of the two readings. Sample-size contingency: because this comparison is conditioned on trajectories that show *any* drift, its qualifying set size is not fixed in advance by the scale-up's 54-trajectory total; the pilot stage's primary go/no-go check (RQ2's walking-skeleton gate) is required to yield at least 10 qualifying trajectories across the scale-up before this RQ is treated as adequately powered — if fewer qualify, the finding is reported descriptively (raw agreement count) rather than as a percentage against an 80% target, and the qualifying-set size is stated alongside the result.

**Expected outcome.** The mixed-effects slope sign and the Mann-Kendall trend sign agree in at least 80% of qualifying trajectories, conditional on at least 10 trajectories qualifying as stated above.

**Falsification condition.** Refuted (given an adequately powered qualifying set) if sign agreement falls below 80%; treated as inconclusive rather than refuted if fewer than 10 trajectories qualify, since the 80% target itself is not well-powered below that count.

**Hypothesis (plain language).** Two independently derived statistical readings of "is this trajectory drifting" should not contradict each other; if they routinely do, neither reading can be trusted on its own.

**Metrics.** Sign-agreement rate among qualifying trajectories; qualifying-set size, reported alongside every result from this RQ.

#### RQ5: Are the three patch-level features load-bearing carriers of the observed drift?

**Setup.** Within each trajectory, regress per-step metric deltas on the three patch-level features (cross-layer import edges, duplication delta, edit locality) plus trajectory fixed effects; compare the explained variance of this model against an ablated model with the three features removed.

**Expected outcome.** Removing the three features from the regression drops explained variance by at least half, indicating the features are load-bearing carriers of the measured drift rather than incidental correlates of it.

**Falsification condition.** Refuted if explained variance drops by less than half (or not at all) when the features are removed — indicating whatever drift exists is not substantially carried by the three hypothesized patch-level mechanisms, and drift prediction would need trajectory-level state instead of per-patch features.

**Hypothesis (plain language).** Whatever architectural drift is observed is explainable, in large part, by concrete and checkable properties of the patches that produced it, not by an unexplained aggregate trend.

**Setup.** Regress trajectory-level erosion-rate estimates on the four declared factors (agent configuration, task type, ordering, lagged prior-erosion state) via likelihood-ratio tests against a null mixed model, each factor's effect assessed net of the other three, Holm-corrected across the factor family.

## Related Work

The closest prior work to this study sits on three sides of the gap being measured. SWE-bench supplies the exact acceptance protocol this paper adopts — patch correctness defined by fail-to-pass and regression test execution on real repository issues — but grades each instance independently from its own fixed base commit. Sas et al.'s empirical study of architectural smells is the closest methodological analog on the classical measurement side, linking source-code changes to the dynamics of cyclic and hub-like dependencies, but only across human-authored open-source commit histories. And the recent agent-code-degradation line — SlopCodeBench and CodeThread foremost — has already established the phenomenon-level headline that iterated agent editing degrades code structure; we concede that headline plainly. What none of the three supplies is this paper's instrument: SWE-bench's acceptance protocol held fixed on a real, mature repository, with erosion identified against the human-authored gold patches for the identical task sequence — a matched counterfactual no unmatched-population comparison can substitute for.

**Degradation and maintainability of agent-authored code.** SlopCodeBench measures structural erosion and verbosity as coding agents iteratively extend their own solutions across evolving specifications, finding erosion rising in the large majority of agent trajectories and agent code substantially more eroded than open-source baselines — but its substrate is greenfield code the agent itself wrote from scratch against synthetic problems, and its human reference is a population of unrelated repositories' git histories, so it cannot isolate agent-attributable erosion on a real codebase from what those specific tasks would have required of anyone. CodeThread constructs controlled build-on-top experiments from repository-level benchmarks and finds downstream agents resolve fewer tasks on agent-written code than on human-written code, with traditional maintainability metrics failing to explain the gap — but its outcome variable is downstream functional resolution, a lagging consequence, not a per-step trajectory of the architectural state itself. Audits of AI-generated code report that more capable models generate more bloated, coupled code, with volume strongly predicting structural degradation — generation-time analyses that do not follow a persistent repository through a test-gated sequence of accepted patches. And work on architectural-smell repair evaluates whether agents can fix existing cross-module smells, the inverse direction of the question studied here. Relative to all four, this study's deltas are the matched same-task-sequence human-gold counterfactual, the dependency-structure estimand measured against frozen per-repository import contracts, the single-shot control separating per-patch-additive from sequence-amplified erosion, and per-patch mechanism attribution.

**Outcome-only agentic software-engineering evaluation.** SWE-bench defines patch correctness purely through fail-to-pass and regression test execution on real GitHub issues; SWE-Lancer argues unit tests are insufficient for judging full-system behavior on freelance software jobs, but replaces them with stronger end-to-end tests rather than any structural check; BOAD discovers multi-agent architectures via bandit optimization under a reward it describes as almost entirely deferred until the final patch outcome. All three define or optimize for correctness purely at the outcome level, with no term — explicit or implicit — sensitive to the dependency structure of the resulting code, so none can distinguish a structurally healthy resolution from a structurally corrosive one that happens to pass the same tests. A related line studies agents *gaming* this gate rather than quietly eroding under it: ImpossibleBench measures models' propensity to exploit test cases directly, SpecBench quantifies reward hacking in long-horizon coding via the gap between visible and held-out test suites, and SWE-Marathon observes reward-hacking behavior in a sizable fraction of ultra-long-horizon task rollouts. That failure mode is disjoint from the one measured here: even a perfectly hack-proof test suite — one no agent could game — would remain architecture-blind, so structural erosion can proceed at full rate under an oracle those benchmarks would certify as sound.

**Multi-round and process-level agent evaluation.** Coeditor models code evolution as an iterative diff-prediction problem, conditioning on a sequence of prior edits within one commit to assist a human developer; EnvConfigTrajEval scores an agent's intermediate planning and repair steps against gold annotations rather than final executability alone, arguing that outcome-only scoring conflates distinct agent behaviors. Both treat process or history as informative, but Coeditor's multi-round conditioning is an assistance mechanism for a single commit, not a longitudinal quality measurement, and EnvConfigTrajEval's process-level view is scoped to one environment-configuration episode rather than the evolving structural state of a persistent artifact across many tasks.

**Longitudinal degradation modeling in adjacent LLM settings.** Time-To-Inconsistency models multi-turn dialogue robustness as discrete-time survival analysis, treating the first inconsistency as a censored survival event with turn-level hazard functions; SimpleTIR identifies compounding distributional drift across turns in tool-integrated agent trajectories and mitigates it during RL training by filtering degraded trajectories. Both supply exactly the kind of temporal, degradation-aware statistical machinery this paper needs, but neither instruments a persistent external artifact: Time-To-Inconsistency's events are conversational, and SimpleTIR's drift is in the model's own generation distribution during training, with environments that reset between episodes rather than accumulate a shared, examinable state.

**Classical software-architecture erosion.** Lehman's laws of software evolution posit that an evolving system's complexity increases unless explicit work is invested against it, derived from release-granularity observation of human-organizational development; Li et al.'s systematic mapping study synthesizes decades of findings on architecture-erosion causes, consequences, and detection, explicitly calling for more empirical studies of erosion in practice; Sas et al. establish the relation between architectural smells and source-code changes across open-source commit histories. All three describe erosion as a phenomenon of human-driven development at release or commit granularity, with no measurement protocol for a controlled, serially executed, test-gated sequence of autonomous agent edits — and no counterfactual design separating task-required structural change from edit-specific degradation, which is the gap this paper's human-gold contrast is built to close.

## Conclusion

This work turns a quiet assumption behind agentic software engineering — that a green test suite means a healthy codebase — into a measurable claim rather than a default belief. The central methodological wager is that "erosion" only becomes a defensible claim once it is checked against three things at once: an acceptance gate independently shown to be structurally blind, a counterfactual trajectory that absorbs whatever structural growth a correct solution would need anyway, and a longitudinal model built for a slow, compounding signal rather than a snapshot comparison. Whichever regime dominates for current coding agents is decision-relevant either way: measurable agent-attributable erosion would mean test-only acceptance gates need a structural companion check before agentic development scales further; a null result would still be valuable, delivering the first *counterfactual-controlled* counter-evidence — a contrast against the humans who solved the identical tasks, which no unmatched-population comparison in the existing agent-code-degradation literature can supply — against the assumption that agentic editing must erode architecture faster than human editing, together with an open measurement harness for re-testing the question at longer horizons and on new agents. Two limitations bound this claim from the outset. The design is scoped to Python repositories with an importable, layered module structure and three studied agent configurations, leaving other languages, architectural styles, and a fully crossed agent-by-backbone design for follow-up. And the static-analysis metrics used here are an explicit proxy for architectural health, not a stand-in for expert architectural judgment — a proxy this paper checks, but does not claim to have replaced, pointing toward a validated, expert-grounded construct as the next methodological target.
