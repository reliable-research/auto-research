ABSTRACT
We investigate a modification of the classical Bounded Model Checking (BMC) procedure that does not handle loops through unrolling
but via modifications to the control flow graph (CFG). A portion of
the CFG representing a loop is replaced by a node asserting invariants of the loop. We generate these invariants using Large Language
Models (LLMs) and use a first-order theorem prover to ensure the
correctness of the generated statements. We thus transform programs to loop-free variants in a sound manner. Our experimental
results show that the resulting tool, ESBMC ibmc, is competitive
with state-of-the-art formal verifiers for programs with unbounded
loops, significantly improving the number of programs verified
by the industrial-strength software verifier ESBMC and verifying
programs that state-of-the-art software verifiers such as SeaHorn
and VeriAbs could not.

INTRODUCTION

Bounded Model Checking (BMC) is a well-established technique for
hardware and software verification [7, 6]. Broadly, bounded model
checkers work by exhaustively checking that no path through a
program leads to an error state [18]. Loops are typically handled
by unrolling. Thus, loops that cannot be statically bounded or have
large static bounds pose problems for software model checkers [40,

23, 27]. In practice, for code involving loops with non-trivial bounds,
BMC can find bugs, but cannot prove correctness. The main alternative to loop unrolling in software verification is to use a loop
invariant to represent the program states that hold for all loop iterations. Loop invariants may be supplied manually [25] or discovered
automatically [2]. Once these invariants are computed, they can be
used for various applications, including proving correctness, code
optimization and refactoring, debugging, and testing.
In the context of BMC, a loop can be replaced by a suitable invariant, resulting in a loop-free program, which classic BMC techniques
can then handle using Boolean Satisfiability (SAT) or Satisfiability
Modulo Theories (SMT) solvers. The challenge here is to synthesize
suitable invariants [51]. This has long been an active area of research, and various approaches exist to discover invariants. These
include abstract interpretation [19], predicate abstraction [24], constraint solving [14, 3], and dynamic analysis [46]. However, none
of these methods have become established, and most are limited to
some particular class or domain of loops and fail to generalize to
arbitrary programs.
With Large Language Models displaying emergent code generation and auto-formalization abilities [15, 57], there has been a surge
in interest in their ability to generate invariants [55]. However,
invariants generated by LLMs are unlike those generated by abstract interpretation, as there are no guarantees that the candidate
formulas generated by an LLM are indeed invariants. Thus, relying
on candidates returned by an LLM can easily lead to unsoundness.
Hence, we combine an LLM with a first-order theorem prover. In
particular, we use the superposition-based prover Vampire [38] to
try and prove that candidate invariants are truly invariant. Candidates for which no proof is found are discarded.
To summarise, we attempt to complement BMC’s existing strengths
in bug finding by strengthening its verification abilities.. We achieve
this as follows. We take a C program and use an LLM to annotate
all loops with candidate loop invariants. The annotated program is
then passed to the ESBMC verifier [42]. During symbolic execution,
when ESBMC reaches a loop, instead of attempting to unroll it,
ESBMC calls Vampire to prove the candidate invariants. If Vampire
successfully proves one or more invariants, the loop is replaced
by a formula asserting the proven invariants, and symbolic execution continues as normal. If the execution reaches an assertion,
ESBMC attempts to prove it as normal i.e. by translation to SMT as
described in Section 2.4.

BMC, in particular, has become an effective and popular verification technique. For loop-free programs, model checkers harness
the surprising effectiveness of SAT and SMT solvers [28] to explore
all program paths and either uncover bugs or verify safety and correctness. We discuss BMC in more depth in Section 2.4. However,
as mentioned in Section 1, and in common with other techniques,
BMC struggles with loops that cannot be statically bound or with
large bounds [27]. Classic BMC works by unrolling loops, which
does not scale well. A common method of handling loops is to use
inductive loop invariants. An inductive loop invariant (or just loop
invariant for short) is a logical assertion that holds at a loop head
whenever program execution crosses this location. Synthesizing
loop invariants is perhaps the main challenge in program verification [50] and has uses in other areas such as static analysis [43].
Due to the issue’s centrality, various approaches have been explored. One approach is to solve a set of recurrence relations using
a constraint solver. This is the approach taken by Ji et al. [36] and
Amrollahi et al. [3], for example. The downside of the approach is
that it is restricted to particular classes of loops. In the case of Ji et
al., their approach is restricted to affine loops, while Amrollahi et
al. target a generalization of the solvable loops.
Another popular approach is dynamic invariant generation [22,
45]. Dynamic generation proceeds by generating a large number
of invariant templates. Actual program runs are then used to filter
the templates. The remaining templates can then be passed to a
verification engine to ensure they are true invariants. The downside
of this approach is that, again, it is limited by the form of the preselected templates.
Abstract interpretation [19, 20] is also widely applied. However, abstract interpretation methods are limited by the domain
of abstraction. There are many other techniques, such as Craig
interpolation [31] and the IC3 approach [11]. However, they all
tend to be limited in the form of the loop they can handle or the
form of the invariant they can produce.
This has led to interest in using neural techniques for invariant
generation. Code2Inv [52] uses deep reinforcement learning to
synthesize invariants as part of a counterexample-guided inductive
synthesis loop. He et al. [32] use a neural net to remove redundant
constraints introduced during abstract interpretation.
There has also been a surge of interest in using Large Language Models (LLMs) for verification. Janßen et al. [35] conduct
exploratory work on getting LLMs to produce invariants. Pei et
al. [48] use an LLM to predict whether a formula is likely to be a
Daikon [22] generated invariant. Likewise, Chakraborty et al. [13]
do not use an LLM to generate invariants directly but instead to
rank candidate invariants. Finally, Wu et al. [55] is the work closest
to ours. The authors use an LLM to generate candidate invariants,
but unlike our approach, this is not integrated into an existing verification technique. We provide a more detailed comparison of our
approach with the associated lemur tool in Section 6.1.

2 BACKGROUND AND RELATED WORK
2.1 Large Language Models
Large Language Models are a form of deep learning model based
on the transformer architecture that has shown proficiency at text
generation and language processing tasks [9]. They are commonly
trained on large datasets and consist of billions of parameters. LLMs
can be fine-tuned for performance on particular tasks, though as the
model size grows, fine-tuning becomes less important [12]. Many
LLMs have been developed, from the well-known ChatGPT [56] to
Claude and Gemini.
It is known that the prompt provided to an LLM is crucial to
the quality of the response received. It is also known that LLMs
respond differently to prompts [10]. This has given rise to the field
of prompt engineering [29]. The two best-known approaches are
the chain of thought [53] and the tree of thought [58].
Chain of Thought. This approach guides the LLM in formulating
an increasingly accurate answer with a more refined and detailed input prompt [59, 58]. White et al. [54] outline four main components
that can be used to construct this type of prompt:
• Input Semantics – what the input will look like, e.g., a custom
grammar and any associated rules.
• Context Control – to provide extra context to the LLM, such
as a specific solved example of what you would like the
LLM to do, thereby increasing the likelihood of the LLM
generating more accurate responses to increase
• Output Customisation – how the output should be presented,
i.e., is there any template that the LLM can populate with its
response?
• Error Identification – for resolving the errors in the LLM generated responses, the improvement of the respective prompt
– which is refining the question for a more appropriate answer (potentially with various approaches).
Tree of Thought. In contrast, in the Tree of Thought approach,
queries are represented as a decision tree, and the responses are
traversed in a breadth or depth-first manner [58]. The traversal
undergoes a purification stage where only the relevant responses
are taken to formulate an overall response. This is ideally used
for more complicated problems that may require a larger, more
complex, and, in some cases, verbose output [58, 41]. This is used
for larger models like GPT-4 and GPT- Turbo - as they have a
significantly higher context window of 8K to 128K tokens.

generated response has some financial cost depending on the token

4.3

Pipeline Modifications

After establishing the initial pipeline, experimentation led to further
modifications.
Filtering Suggested Invariants. We observed that generated invariants often led to parsing errors during verification. There were
two main classes of parsing errors:
(1) The LLM generated incorrect C code, and
(2) Hallucinating variables, i.e., generating an invariant over a
program variable that did not exist in the program.
Class 2, hallucination, occurred rarely during our experiments
and did not appear to impact the result significantly. We inspected
the invariants generated on all failed runs, and no failures were
due to hallucination issues. Most issues fell into the first class, and
we focused on this. Instead of providing further constraints in the
prompt (i.e. attempting to teach the LLM what a correctly formed
invariant should look like), we performed a lightweight syntactic check on the generated invariants. This utilized a relatively
constrained regular expression
__invariant\((\w|\s|\|\||&&|!|=|<|>|\?|:|\(|\))*\);
to limit the invariants used for verification. Each invariant is checked
against the pattern and discarded if it does not match. This allows
an iteration to proceed even if some generated invariants are syntactically invalid.

6.1 Comparison with lemur Framework
The lemur Framework by Haoze et al. [55] is similar to our work
in that they use an LLM to generate program invariants and use
ESBMC [42] and UAutomizer [33] to verify programs. We compare
our two approaches and compare results.
Comparing Approaches. Lemur introduces a framework for automated program verification which decomposes the verification task
into sub-goals and utilizes an LLM to complete some creative subgoals (generating and repairing loop invariants) and verification
tools ESBMC [42] and UAutomizer [33] to complete verification
sub-goals. This approach differs from ours as it is reactive. If a
particular invariant is not useful, the framework can attempt to
repair it. Another difference is that as it does not need to reason
about invariants directly, it can easily handle complex programs.
However, as the framework treats verification tools such as ESBMC
as black-boxes and communicates via assertions and assumptions

CONCLUSION

In this paper, we have explored using LLM-generated invariants
to replace loops in the context of BMC with promising results. On
programs that contain unbounded loops, our tool ESBMC ibmc outperforms the current best ESBMC strategy for such benchmarks, kinduction. Furthermore, our approach handled certain benchmarks
that none of the current state-of-the-art verifiers can. Moreover, we
have demonstrated that by pairing an LLM with a full first-order
prover, we can go beyond quantifier-free invariants and handle
invariants and assertions involving arbitrary quantification. That
being said, our work also raises many interesting questions that we
hope to address eventually.
