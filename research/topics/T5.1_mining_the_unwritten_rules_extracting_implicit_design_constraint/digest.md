## N6 Methodology

### `overview` **[HYPOTHESIS]**

"A two-stage measurement study. **Stage 1 — pilot (= the seed's minimal experiment, 评审语料 →
约束目录 → 对 agent patch 的违规分布统计):** on ~5 high-review-volume Python repositories drawn
from SWE-bench Verified's repository set (e.g., django, scikit-learn, sympy, matplotlib,
sphinx), collect all in-line PR review threads with verdicts (M1); run LLM extraction of
change-inducing constraint candidates (M2); cluster candidates into per-repo catalogs under
the three seed categories with dual human categorization (M3); apply each repo's catalog to
test-passing agent patches from public SWE-bench leaderboard submissions and to the matched
human gold patches (M4); and validate both the catalog and the violation judge against
human-annotated held-out review threads and human verdicts (M5). A pilot gate (extraction
precision ≥ 0.5 on a 100-candidate sample) decides whether prompts/filters are revised before
proceeding. **Stage 2 — scale-up:** extend M1–M4 to 50–100 repositories across ≥3 languages
and ≥3 agent systems to test whether the pilot's category-wise violation distribution
generalizes, and release the catalogs plus violation-labeled patch set as an artifact."

### `key_components`

- `id`: "M1", `name`: "Review Corpus Collector" **[HYPOTHESIS]** — "Harvests, via the GitHub
  GraphQL API, all PR review threads for target repos at the granularity (repo, PR, thread,
  in-line comment, anchored diff hunk), joined with review verdicts (APPROVED /
  CHANGES_REQUESTED), merge status, and follow-up commits; computes for each comment a
  *change-inducing* flag (a later commit in the same PR modifies the anchored lines), which
  serves as a behavioral signal that the comment expressed an enforced expectation."
- `id`: "M2", `name`: "Constraint Extractor" **[HYPOTHESIS]** — "LLM pass over each
  change-inducing comment plus its diff hunk and ±20 lines of file context, emitting a
  structured candidate record: {normalized imperative rule statement, scope (file/module/
  repo-wide), trigger condition, provisional category, evidence link to the source thread};
  comments judged non-generalizable (one-off bug, question, praise) are emitted as
  no-constraint and dropped. A keyword/directive-pattern extractor (regex over 'should/must/
  please/avoid/never' plus code-element mentions) is implemented alongside as the non-LLM
  baseline."
- `id`: "M3", `name`: "Constraint Catalog Builder" **[HYPOTHESIS]** — "Embeds candidate rule
  statements (sentence-embedding model), clusters them (agglomerative/HDBSCAN), LLM-merges
  each cluster into one canonical catalog entry with a support count (# distinct threads and
  # distinct reviewers); entries with support < 3 distinct threads are quarantined, not
  admitted. Category labels (error handling / architectural convention / API convention /
  other) are assigned independently by two human annotators; disagreements adjudicated,
  Cohen's kappa reported."
- `id`: "M4", `name`: "Agent-Patch Violation Checker" **[HYPOTHESIS]** — "For each
  test-passing agent patch (sourced from the public SWE-bench experiments repository of
  leaderboard submissions, ≥3 distinct agent systems) and its matched human gold patch:
  retrieve the applicable catalog entries for the touched files/modules, then run an
  LLM-judge per (patch, rule) pair that outputs violated/compliant/not-applicable with a
  localization (file:line) and a one-sentence rationale; per-patch output is the set of
  violated rule ids with categories."
- `id`: "M5", `name`: "Human-Verdict Validator" **[HYPOTHESIS]** — "Two validation
  instruments: (a) *catalog validity* — two annotators judge a stratified sample of catalog
  entries as genuine project constraints or spurious (precision), and independently mine
  constraints from 100 held-out review threads to estimate what the pipeline missed (recall
  proxy); (b) *judge validity* — on a sample of (patch, rule) judgments, two annotators label
  violation/no-violation blind to the LLM judge, giving judge-vs-human agreement (kappa), and
  flagged agent-patch violations are cross-checked against what human reviewers actually
  demanded in the nearest analogous historical threads."

## N10 Threats / Self-Limitations

1. `threat_id`: "t1", `category`: "construct", `description` **[HYPOTHESIS]**: "The three-way
   category scheme and the notion of 'constraint violation' are operationalizations imposed by
   the pipeline (M2/M3), and may not correspond to how reviewers actually reason — a rejection
   may span categories or reflect a concern the taxonomy cannot express; likewise the
   change-inducing filter operationalizes 'enforced expectation' and may capture one-off fixes."
   `mitigation` **[HYPOTHESIS]**: "Dual independent categorization with adjudication and
   reported kappa, an 'other' escape category, entry-level (not only category-level) result
   reporting, and the ≥3-distinct-threads support threshold before catalog admission."
2. `threat_id`: "t2", `category`: "internal", `description` **[HYPOTHESIS]**: "Human review
   verdicts — the ground truth — are noisy and confounded: reviewers disagree, norms drift over
   time, and CHANGES_REQUESTED can reflect scope or timing rather than convention violations;
   additionally, the LLM judge (M4) may share failure modes with the LLM agents being judged,
   inflating or deflating measured violation rates."
   `mitigation` **[HYPOTHESIS]**: "Restrict mining to a recent time window per repo;
   aggregate across multiple reviewers/threads; gate all automated violation labels on a
   judge-vs-human κ ≥ 0.6 on n=400 dual-annotated (patch, rule) pairs; use a judge model from
   a different family than the evaluated agents."
3. `threat_id`: "t3", `category`: "external", `description` **[HYPOTHESIS]**: "Pilot findings
   come from a handful of mature, review-heavy, Python OSS projects (the SWE-bench Verified
   repos) and from the specific agent systems on its public leaderboard; results may not
   generalize to other languages, younger or closed-source projects, low-review-volume
   ecosystems, or future agent generations."
   `mitigation` **[HYPOTHESIS]**: "The staged design: Stage 2 scales to 50–100 repos across
   ≥3 languages and additional agent systems, and per-repo distributions are reported so
   heterogeneity is visible rather than averaged away."
4. `threat_id`: "t4", `category`: "conclusion", `description` **[HYPOTHESIS]**: "Statistical
