## Stage 1 — Problem Definition

Core question (seed, near-verbatim): do consecutive agent patches on the same repository progressively erode its architecture — every step passing the test suite, yet cumulatively corroding layering and dependency structure (每步都过测试，累计却腐蚀分层/依赖结构)? And what does the erosion rate depend on?

Formulation (digest N1): a longitudinal repeated-measures study. *Inputs*: (1) repositories with a declarable reference architecture (module layers, import contracts); (2) a chronologically ordered sequence of ~20 realistic issue-derived tasks per repo; (3) coding agents (scaffold × backbone); (4) the repo's test suite + per-task fail-to-pass tests as the **sole** acceptance gate; (5) the human-authored gold patches as the counterfactual arm. *Outputs*: per-step architecture-metric time series; an erosion-rate statistic per trajectory (mixed-effects slope; time-to-first-violation); agent-vs-human contrasts; factor attribution (agent, task type, ordering, prior erosion state) and patch-level mechanism profiles (cross-layer imports, duplication, edit locality). *Ground truth constraint* (seed, [GIVEN]): 真值 = 静态分析度量 — architectural state is defined by static-analysis metrics, not architect judgment.

Scope boundary: T5.4 makes no claim about single-patch detectability (T5.2's question) and no claim about repair; it measures the accumulation phenomenon and its correlates.

**Critic:** (1) "Erosion" is defined only implicitly; without a counterfactual it is unidentifiable — some structural change is *necessary* (a feature legitimately adds coupling), so raw metric worsening is not erosion (digest C2). The definition must build the counterfactual in, not bolt it on. (2) "真值 = 静态分析度量" is a construct-validity landmine if stated as ground truth *simpliciter* — reviewers of the SE persuasion will ask whose architecture the import-linter contracts encode. (3) The T5.2 boundary is stated, but the definition should also say what T5.4 *cannot* conclude that T5.2 can (per-patch causal attribution of intent-level violation) to pre-empt "why two papers?" (4) ~20 steps per trajectory is asserted in the formulation before feasibility has justified it.

**Refined:** Erosion is *defined* as a contrast: the difference in architecture-metric trajectory between the agent arm and the human-gold arm on the identical task sequence (step×arm interaction), not the raw slope — necessary coupling appears in both arms and cancels. Static-analysis metrics are the *operationalization*, declared once (import-linter contracts frozen from documented package structure before any run) and validated by a blinded expert spot-check (~60 snapshots) — "ground truth" is thus scoped to "pre-registered instrument," which is what the seed's constraint actually licenses. The two-paper division of labor is made explicit in the definition: T5.2 answers "can a single test-equivalent patch violate design, and can we detect it?" (existence + detector validity); T5.4 answers "does it *happen* under real agent workflows, how fast, and what predicts it?" (prevalence + dynamics) — T5.4 inherits detector validity from T5.2 rather than re-arguing it, which is precisely why the composition is efficient. Trajectory length (~20 steps) is downgraded from a design constant to a pilot-determined parameter with a floor (≥12 surviving steps after rebase attrition, see Stage 6 gates).

## Stage 2 — Motivation

1. **The acceptance oracle is architecture-blind by construction.** The dominant agentic-SE evaluation paradigm defines correctness as fail-to-pass + regression test execution (SWE-bench); even its critics substitute stronger *tests*, not structural checks (SWE-Lancer). Test suites encode input–output behavior, not dependency direction or module boundaries — so a hidden, compounding maintainability cost is invisible to every pipeline that gates on tests alone.
2. **Production telemetry now suggests the cost is materializing.** Channel-relayed figures attributed to Faros AI production telemetry report defect-escalation rates rising from ~9% to ~54% in AI-heavy engineering organizations [VERIFY: channel-relayed, exact metric definition, population, and time window unverified — locate the primary Faros report and confirm the metric is defect escalation before any use in a paper; if unverifiable, drop from the paper and keep only peer-reviewed/first-party sources]. Adjacent public evidence points the same way: GitClear's repository analyses report rising code duplication and declining refactoring share coinciding with AI-assisted authorship [VERIFY: GitClear 2024/2025 reports — industry white papers, cite as indicative, not causal]. None of this telemetry can separate architectural erosion from other causes — which is exactly the controlled measurement this study supplies.
3. **The erosion literature has never seen this editing regime.** Lehman's law of increasing complexity and the architecture-erosion literature (Li et al. 2022 mapping study; Sas et al. 2021 smells-vs-changes) are built entirely on *human-driven* change histories at human cadence. Autonomous agents change the cadence, the acceptance process, and plausibly the mechanism; prior findings cannot be assumed to transfer, and Li et al.'s own call for more empirical erosion studies marks the gap.
4. **Adjacent agentic results make compounding plausible.** Multi-turn degradation is documented in the model's own distribution (SimpleTIR) and in conversational consistency (Time-To-Inconsistency); Regression Accumulation (arXiv:2607.01855) documents functional regression accumulating across programming turns. The *persistent-artifact* version — structure decaying while every functional check passes — is the untested case.

**Critic:** (1) Motivation 2 is doing headline work on an unverified relayed number; if it evaporates the motivation must stand without it — currently it reads load-bearing. (2) A skeptic's null is live and unaddressed: agents are *conservative* editors (minimal diffs to pass tests) and might erode *slower* than humans who refactor opportunistically; the motivation should embrace this as a genuinely two-sided question — the measurement is valuable either way, which strengthens, not weakens, a Tier-2 measurement paper. (3) Motivation 1 proves blindness of the oracle, not existence of the phenomenon — the leap from "tests can't see it" to "it happens" is exactly what the study must measure, so the prose must not presuppose the answer (the digest's predicted directions are predictions, not premises). (4) No motivation states why *longitudinal* is needed over T5.2-style single-edit analysis — the increment must be motivated, not just bounded.

**Refined:** Motivation 2 is demoted to "timeliness signal, not evidence": the paper's evidential base is the controlled experiment; telemetry (Faros [VERIFY], GitClear [VERIFY]) appears only as context for why the question is being asked now, each tagged and dropped without structural damage if unverified. The two-sided framing is promoted to the headline: the study adjudicates between *erosion* (agent > human drift), *parity*, and *conservatism* (agent < human drift — plausible because agents under-refactor), and all three outcomes are publishable findings with different practical consequences (gate design vs. reassurance vs. "agents ossify code"). The longitudinal increment over T5.2 is motivated mechanically: single-edit analysis cannot observe (a) compounding (whether prior erosion accelerates subsequent erosion — a lagged-state effect), (b) ratchet effects (violations that are individually reversible but collectively locked in by later edits building on them), or (c) rate — and rate is the actionable quantity for deciding *how often* a structure gate must run in production pipelines. Motivation 1's prose is audited to keep the phenomenon hypothetical until Stage 6 measures it.

## Stage 3 — Related Work

## Stage 4 — Sub-Problems

1. **SP1 — Constructible serial task sequences.** *The named hard part, and the audit's stated main cost.* SWE-bench instances assume their original base commits; after the agent's patches diverge from real history, later tasks' context and fail-to-pass tests may not apply (conflicts, moved code). Must build a sequence harness that rebases tasks/tests onto the evolving checkout, logs attrition as a first-class outcome, and keeps arms comparable. Everything else waits on this.
2. **SP2 — The per-step architecture instrument.** Metric suite (import-graph cycles, frozen layer-contract violations, smells, propagation cost, complexity, duplication) + T5.2 detector reuse; contracts declared and frozen pre-run; construct-validity spot-check.
3. **SP3 — Counterfactual identification of erosion.** Human-gold arm (same tasks, same order), single-shot arm (same agent, no accumulated history — isolates the *sequence* effect from the *agent* effect), random-order arm. Without SP3 the study measures drift, not erosion.
4. **SP4 — Slow-drift statistics.** Per-step deltas are small vs. step-to-step variability (patch sizes vary by orders of magnitude); need mixed-effects slopes with trajectory random effects, Mann-Kendall checks, survival-style time-to-first-violation, Holm correction across metric families — not before/after snapshots.
5. **SP5 — Attribution under combinatorial cost.** Every condition costs a full serial trajectory (not parallelizable within itself); factor space (agent × repo × ordering × task type × prior state) collides with budget. Resolve via a deliberately small factorial + within-trajectory mechanism features (regressing per-step deltas on patch features) that yield attribution without extra trajectories.

**Critic:** (1) SP1's rebase attrition is not just a feasibility nuisance — it is a *selection bias*: tasks that survive rebasing after agent edits may be systematically easier/more localized, and attrition may differ *between arms*, contaminating the SP3 contrast; the sub-problem list treats attrition as logging when it is a validity threat. (2) SP3's single-shot arm is listed but its analytical role (decomposing agent effect vs. accumulation effect) deserves promotion — it is the study's cleanest causal lever. (3) SP4 omits the pilot power question: with ~20 steps and 3 seeds, what slope is even detectable? (4) No sub-problem owns reproducibility (model drift, nondeterminism), which for a longitudinal design is aggravated (a mid-study backbone deprecation breaks a trajectory arm).

**Refined:** SP1 is re-scoped to "sequence construction *with arm-symmetric attrition control*": identical rebase/drop rules applied to all arms, primary contrasts restricted to the task intersection completed by all arms, attrition reported per-arm with a differential-attrition threshold (>15pp between arms voids the primary contrast for that repo). SP3 promotes the decomposition explicitly: erosion(total) = [agent single-shot − human] (patch-quality effect) + [agent serial − agent single-shot] (accumulation effect) — the paper's central identity, each term separately estimable in the design. SP4 gains a pilot-based power gate: estimate per-step delta SD from the pilot's 3 seeds and compute the minimal detectable standardized slope before committing to scale-up (go/no-go G2, Stage 6). Reproducibility is added inside SP1's harness spec: pinned model versions + temperatures, one fully re-runnable open-weight arm, all accepted-patch sequences and per-step snapshots released — a longitudinal study whose trajectories cannot be replayed is not a measurement.

## Stage 5 — Methods

**5.1 Task-sequence benchmark design (SP1).**
- *Source*: SWE-bench Verified instances grouped by repo, ordered by issue creation date; primary repos django/django, sympy/sympy, astropy/astropy (densest coverage). Secondary: SWE-bench Lite for ordering-control fill.
- *Harness*: run each task in the benchmark Docker env against the **current agent-evolved checkout** (not the instance base commit); mechanically rebase fail-to-pass tests onto that checkout; tasks whose tests do not apply cleanly are dropped under arm-symmetric rules and logged (sequence attrition = first-class outcome). One commit per accepted task.
- *Acceptance gate (architecture-blind by design)*: rebased fail-to-pass tests + regression suite, exactly the SWE-bench correctness definition; **no linters, no structure checks** — so every counted violation is one the test gate admitted. ≤k retries then skip.
- *Fallback* (if rebase survival <60% in pilot): a curated synthetic sequence — 20 feature/bugfix tasks authored against one mid-size layered OSS app — sacrificing task realism for guaranteed sequence validity; reported as such.

**5.2 Static-analysis metric suite (SP2, per accepted step).** (a) import graph via grimp/pydeps; cyclic-dependency count = modules in SCCs of size >1; (b) layering violations against frozen import-linter contracts (T5.2 detector configuration reused verbatim); (c) architectural smells (cyclic, hub-like, unstable dependency; Arcan-style); (d) MacCormack propagation cost, fan-in/out; (e) radon cyclomatic complexity + maintainability index; (f) duplication % (jscpd). Instrument frozen before any run; blinded expert rating of ~60 sampled snapshots as construct check.

**5.3 Arms & mechanism profiling (SP3, SP5).** Arms: agent-serial (3 configs: e.g., OpenHands+frontier, SWE-agent+frontier-B, Agentless+open-weight) × 2 orderings × 3 seeds; human-gold serial; agent single-shot; random-order control. Mechanism profiler per accepted patch (both arms): LOC ±, files/modules touched, new import edges + layer-crossing flag, duplication delta, edit locality (graph distance among touched modules).

**5.4 Erosion trajectory statistics (SP4).** Primary: mixed-effects `metric ~ step × arm + (step | repo:seed)`; the step×arm interaction = erosion-rate difference; Mann-Kendall per trajectory as nonparametric check; discrete-time survival for time-to-first-new-violation (censoring never-violating trajectories; adapted from Time-To-Inconsistency); Holm–Bonferroni across 6 metric families; effect sizes = standardized slope difference + Cliff's δ on per-trajectory slopes. Decomposition identity from SP3 estimated as two planned contrasts. Mechanism: paired Wilcoxon on patch features (agent vs. human, same task) + within-trajectory regression of per-step metric deltas on features.

**Critic:** (1) The gate's ≤k retries hides a confound: retry count may correlate with task difficulty *and* with structural damage (desperate patches are hackier) — retries must be logged and modeled, not just capped. (2) Human-gold patches were written against the *true* historical base, then applied to a diverged checkout — they may conflict too, and hand-fixing them injects experimenter edits into the control arm; the method must state the conflict policy symmetric to the agent arm. (3) Metric families are correlated (cycles ↔ smells ↔ propagation cost); Holm across 6 "families" understates effective correlation structure — pre-register one primary metric (layering-violation count, the T5.2-validated one) and demote the rest. (4) Duplication (jscpd) will be dominated by test-file boilerplate unless scoped; measure production code and test code separately. (5) 3 agent configs conflate scaffold and backbone (not crossed) — attribution claims must be worded as "configuration" effects, or one crossed cell added.

**Refined:** Retry count enters the mixed model as a per-step covariate and is reported descriptively per arm (also interesting on its own: do retries predict structural damage?). Human-gold conflict policy: identical mechanical rebase as the agent arm; gold patches that conflict are dropped *and the same task is then dropped from all arms* (intersection rule), never hand-fixed — keeping the control arm experimenter-free. Primary endpoint pre-registered as layering-violation count (T5.2-validated detector; the composition made load-bearing), with cyclic-dependency count as co-primary and everything else secondary/exploratory; correlation among metrics reported as a supplementary matrix. Duplication and complexity computed on production code only, tests excluded (reported separately in appendix). Attribution wording fixed to "agent configuration" throughout; one crossed cell (OpenHands × open-weight) added if budget allows, as the minimal scaffold-vs-backbone probe.

## Stage 6 — Experiment Design

**Arms (scale-up).** 3 repos × 3 agent configs × 2 orderings × 3 seeds = 54 agent-serial trajectories (~20 steps each ≈ 1,080 step-observations) + per-repo human-gold (6) + single-shot (3) + random-order (3) controls. Pilot: 1 repo (django) × 1 agent × 1 ordering × 3 seeds ≈ 60 task-runs + 1 human-gold trajectory.

**Scale & compute estimate.** Pilot ≈ 60 runs × $1–5 ≈ **$100–300 API + ~1 CPU-day static analysis**; ~1 person-week. Scale-up ≈ 1,080 runs ≈ **$2k–8k API**, open-weight arm ≈ 1 A100-GPU-week local, static analysis minutes/snapshot; expert spot-check 20–40 hours. Total: low-thousands USD, **2–3 person-months** — the benchmark harness (SP1) is the dominant cost, as the audit flags.

**Go/no-go gates.**
- G1 (pilot, hard): rebase survival ≥ 60% of tasks per sequence *and* differential attrition between agent and human-gold arms ≤ 15pp. Fail → invoke synthetic-sequence fallback (design continues, realism claim narrows).
- G2 (pilot): power check — seed-level slope SD implies a minimally detectable standardized slope; if the pilot's observed agent-vs-human slope gap is < 1/3 of the detectable threshold, scale-up as-designed is futile → lengthen trajectories (fewer, longer sequences) instead of adding conditions.
- G3 (pilot): agent task-acceptance rate ≥ 40% (else sequences stall and "longitudinal" collapses to 5-step stubs; remedy: easier task filter, more retries — logged per the retry covariate).
- Outcome-neutrality clause: erosion, parity, and conservatism are all reportable findings; there is no result-shaped no-go.
