# The Trace Is Not the Truth: Measuring Attribution Blind Spots under Schema-Valid Tool Corruption

## Introduction

Automated failure attribution for LLM agents — reading a failed trajectory and naming whether the plan, a tool, or the execution layer is to blame — is being industrialized to drive real interventions: retraining planners, patching tools, and curating training data. The Who\&When benchmark motivates its own release by observing that manual attribution has become prohibitively expensive and inconsistent, and AgenTracer frames its learned tracer as the interface between observing a failure and repairing the system that produced it. In both framings the attribution verdict is not academic: each diagnosis implies a different fix — retrain the planner, strengthen the execution controller, or patch the tool wrapper — so the *correctness* of the verdict, not merely its availability, is what determines whether the repair lands on the component that was actually broken.

That correctness is now known to be at risk from one direction and untested from another. A recent line of work has established that *agents themselves* over-trust corrupted tool output: TOOLMAZE reports recovery rates collapsing under implicit, semantically corrupted returns that pass every surface check, driven by systemic over-trust, and ToolGate finds that a wrong tool output can overwrite an agent's already-correct belief. This settles that a schema-valid lie — a tool return that is syntactically valid, parses cleanly, and passes every schema check, but is simply the wrong number, the wrong entity, or a stale reading — can steer an agent off course. It leaves open the question one level up, which is the question we ask: when such a lie causes a failure, does the **diagnostic layer built to catch faults** inherit the same lie and misroute the repair? Every attribution method proposed so far reads the trajectory log as trustworthy evidence of what happened, and none contains a step that asks whether the log's own tool observations might themselves be wrong. If the attribution layer over-trusts the trace the way the agent did, then the very tool that broke escapes blame, an innocent plan or execution layer is retrained in its place, and the fix cements the wrong lesson while the real defect recurs.

There is a principled reason to expect exactly this failure, inherent to the attribution problem rather than to any one tool. Any method that localizes fault from a trajectory faces an evidential circularity: the evidence it reasons over is generated by the component whose guilt it is trying to establish — the trace is at once the crime scene and the only witness, and when the witness lies, a diagnosis that trusts it blames the wrong suspect. Concretely, when a schema-valid lie feeds a locally reasonable plan step, the plan step *looks* defective on its face, because separating "the plan was genuinely broken" from "the plan was a sound response to false evidence" requires a counterfactual — what this step would have looked like given the correct observation — that no deployed attribution method has access to. The validity checks these pipelines run certify the *form* of an observation, never its *content*; a wrong departure date in a well-typed JSON field, a stale balance under the correct schema, or the wrong entity under a plausible name leaves no surface trace for a form check to catch. In long-horizon agents the difficulty compounds: a single early corruption contaminates many later decisions, making the downstream behavior look progressively less rational while the original tool fault becomes ever harder to see.

The nearest existing work approaches this from adjacent angles, but none measures whether attribution correctly localizes a well-formed lie. On the attribution side, Who\&When formalizes the task as identifying the agent-step pair whose correction flips a failed trajectory to success, and a fast-growing benchmark line — TraceElephant on full-trace observability, AgentRx and AgentHallu on step-level fault and hallucination attribution — extends it, but all exercise their definitions on naturally occurring agent mistakes, never on a corrupted-yet-well-formed observation whose ground truth is the tool. Causal Agent Replay attributes failures by intervening on a step and re-executing, sharing our counterfactual machinery, but uses it *as the attribution method* over ordinary trajectories rather than as an oracle for constructing verified tool-corruption ground truth. AgenTracer trains a tracer with counterfactual replay and programmatic fault injection, but its fault universe is agent *actions*, not tool *returns*. On the tool-reliability side, benchmarks such as Failing Tools and TOOLMAZE inject silent no-ops, data staleness, and corrupted state and measure whether the *agent recovers* — not whether any downstream diagnosis localizes the fault. Security work on the tool channel (ChatInject, MCP-SafetyBench) measures whether an instruction-bearing payload *succeeds as an attack*, a different threat model from a plainly wrong value in an ordinary field. And lightweight runtime supervisors such as SupervisorAgent trigger on explicit errors, repetition, or excessive observation length — exactly the signals a schema-valid corruption does not emit. In short, prior work has separately established that agents over-trust corrupted tools, that attribution can localize agent mistakes, and that counterfactual replay can attribute failures; no prior work joins them to measure whether attribution methods correctly localize failures caused by schema-valid but semantically false tool observations. That is the gap we occupy.

Turning this into a credible measurement is itself the technical challenge, because a sound study must certify two properties that a naive injection would conflate into one mutation and thereby confound. **First**, a corrupted observation must be provably *invisible* — indistinguishable from a valid return by every surface check an attribution method could run — or the study only measures whether methods bother to validate their input. We enforce invisibility with three independent legality gates: schema re-validation, parser acceptance, and a contextual-plausibility screen run by a model disjoint from any judge or agent backbone. **Second**, and orthogonally, a corrupted observation must be provably *decisive* — verifiably the cause of the failure, not merely correlated with it — since a corruption can be undetectable yet incidental, or decisive yet detectable, and only separating the two makes a `tool`-layer ground-truth label defensible. We establish decisiveness with a counterfactual twin-replay oracle: a candidate joins the treatment set only if the corrupted run fails the task's programmatic checker *and* the twin, with the original observation restored at the same step, succeeds. Holding these two properties apart — one certified by the legality gates, the other by twin-replay — is the enabling move that makes any measured misattribution a property of the *method* rather than an artifact of the *construction*, and it is the axis on which we differ from replay-based attribution methods, which re-execute to *assign* blame but never separate undetectability from decisiveness to *construct* verified ground truth.

On this verified testbed we run existing LLM-judge, trained-tracer, and runtime-monitor attribution methods, blinded to injection metadata, against two matched controls: an *overt-tool-error* arm that shares the tool-layer root cause but emits a visible signal, and an *agent-side-fault* arm that injects the identical wrong value into the agent's own action rather than the tool's observation. The overt-error contrast yields the **Δ-trust gap** — how much a method's misattribution rate rises when the same tool fault is silent rather than signalled — but because an overt error typically truncates a trajectory at the fault step while a silent corruption lets the agent run on, we treat fault-to-manifestation distance as a named confound of that contrast, report the gap stratified by post-fault suffix length, and rest the channel-specificity claim on the agent-side-fault contrast, which carries the identical wrong value at a different causal locus and is immune to it. A one-sentence *trust-license* prompt, added to each LLM-judge and licensing distrust of tool observations, then probes the mechanism: if a method's verdict measurably improves given only a license to distrust evidence it already had, the bias is a removable trust default rather than a hard capability ceiling. Because different methods report verdicts in incompatible native vocabularies — an agent name, a free-text rationale, a discrete flag — we fix a per-method mapping onto the shared {plan, tool, execution} ontology *before any result is seen* and report its inter-annotator reliability as a precondition for trusting any downstream number.

Because this is a measurement study, not a system that competes with a baseline, we pre-register every hypothesis, estimand, threshold, and fallback before collecting data, so that a disconfirming outcome is a clean finding rather than something reinterpreted after the fact. Across **[N]** replay-verified trajectories spanning **[K]** task domains and **[M]** attribution methods, we report that current methods exhibit a Δ-trust gap of **[XX]** percentage points — they misattribute schema-valid lies that much more often than matched overt tool errors — that this inflation is specific to the tool-observation channel, with the agent-side-fault arm staying within **[X]** points of the overt-error control and the gap surviving suffix-length stratification, and that among misattributed cases blame skews toward the plan layer in **[YY]%** of cases, strengthening for subtle, late-trajectory, numeric and stale-value corruptions. The single-sentence trust license reduces tool-corruption misattribution by **[ZZ]** points for **[k]/3** judge variants while inflating false tool-blame on genuine plan failures by only **[AA]** points — evidence that part of the failure is a removable trust prior rather than an unavoidable inability to reason counterfactually — yet a majority of the gap remains, because knowing that observations may lie does not tell a method *which* observation lies. We evaluate over tool-calling tasks from AgentDojo and long-horizon assistant tasks from GAIA, using Who\&When's human-annotated logs as an independently sourced control of genuine plan failures.

In summary, we make the following contributions:

- We move the study of tool-output over-trust up one level, from *whether agents are fooled by schema-valid lies* — already established for agents — to *whether the attribution layer built to catch faults is fooled too, and misroutes repair as a result*, formalizing the structural asymmetry that makes this possible: validity checks certify a tool observation's *form* while the diagnosis consumes its *content* as an unquestioned premise.
- We build a counterfactual-replay-verified corruption testbed that separates *causal decisiveness* from *surface undetectability* as two independently certified properties of an injected fault — the axis on which it differs from replay-based attribution methods that re-execute to assign blame but never construct verified corruption ground truth.
- We design a matched-control protocol — overt tool errors and an agent-side-fault arm carrying the identical wrong value at a different causal locus, with post-fault suffix length controlled — that isolates whether a measured attribution bias is specific to the tool-observation channel.
- We introduce a minimal trust-license prompt intervention that distinguishes a removable trust default from a deeper counterfactual-reasoning limitation, yielding a concrete, falsifiable design recommendation either way.
- We empirically characterize the **direction** of misattribution and its dependence on corruption type, locus, and subtlety across **[M]** attribution methods — showing not merely *that* current methods fail under lying evidence but *where* blame is redirected — reporting a Δ-trust gap of **[XX]** points and a plan-blame skew of **[YY]%** on the pre-registered treatment set.

## Motivation

A failure attribution system exists to answer one practical engineering question: **what should we fix?** If an agent fails because its planner chose an impossible route, the planner needs better decomposition or training data. If it fails because execution skipped a required step, the controller needs stronger state tracking. If it fails because a tool returned wrong information, the fix is different again: validate the tool, patch the wrapper, add a cross-check, or mark the observation untrusted. The premise of automated attribution is that a machine can read the trace and route the repair to the right one of these.

The danger is that in the final trace these cases can look identical. Suppose an agent books the wrong flight because the travel tool returned a valid JSON response carrying the wrong date. The downstream plan now looks irrational — it selected a flight that does not match the request — and a judge reading the trace blames the planner for poor reasoning. But from the agent's local perspective the plan was the correct response to the evidence it was handed; the fault lies upstream, in an observation that read `412.00` when the truth was `1,412.00`. Every value on the trace is well-formed. The only visible anomaly is the plan's choice, so the plan takes the blame, and a team retrains a planner that was never broken while the stale-reading defect recurs on the next task. This is not a contrived edge case: silent value corruption — stale caches, unit mismatches, truncated lists, off-by-one entity resolution — is the ordinary failure mode of real tool ecosystems, and it is exactly the mode that emits no signal for a validity check to catch.

Recent work has shown that agents are fooled by exactly this kind of lie — that they over-trust semantically corrupted but well-formed tool output and fail to recover. But being fooled at *run time* and being fooled at *diagnosis time* are different failures with different consequences. An agent fooled once produces one bad trajectory. An attribution layer fooled systematically produces a bias that feeds automated repair loops: it triggers the wrong retraining signal, patches the wrong module, or teaches a system to distrust a planner that behaved correctly under false evidence — and it does so silently, because its verdicts remain well-formed too. The problem this paper isolates is therefore the gap between **valid format and valid evidence** as it appears not in the agent but in the diagnostic layer meant to be its safeguard. Existing reliability checks catch visible tool failures — exceptions, malformed output, timeouts, missing fields. But an observation can have the right keys, the right type, and a plausible value, pass the parser and the schema, and still be false; a tool observation can be formally valid while epistemically unsafe, and once it enters the trace, any attribution method that reads the trace without questioning the observation channel inherits the same false premise the original agent did.

The insight our study turns into a measurable question is thus simple to state: *the trace is not always the truth; in tool-using agents, the trace may contain the very fault that attribution is meant to diagnose.* Rather than re-asking whether agents are robust to bad tools — a question recent benchmarks have answered — we ask whether the debugging pipeline built to localize faults can still find a fault that hides inside a well-formed observation. An agent may reasonably fail under corrupted evidence; the attribution layer should nonetheless name the corruption as the cause. If it cannot, the automated repair systems built on top of it are systematically misdirected — and the goal of this paper is to measure, under pre-registered conditions, whether and in which direction that misdirection occurs.
