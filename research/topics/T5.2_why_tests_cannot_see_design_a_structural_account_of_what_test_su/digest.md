**[HYPOTHESIS]** — what the N3 works fail to do relative to this idea's core question. Each item cites its N3 `citation_key` verbatim; `grounding_check=true`.

- L1: "The binary code-test matrix formalizes discrimination power, but its rows are *functionally wrong* programs (failing on trusted tests by definition); it has no notion of a program that is functionally equivalent yet design-violating — such a variant is an all-pass row, invisible to a rank-of-failures analysis." `affects_works`=["[BinaryMatrixTests, OpenReview:RomWar2kVN]"]. `limitation_type`="generalizability".
- L2: "The discrimination reward defines a good test suite purely as one that *rejects imperfect (functionally wrong) programs*; a convention-violating-but-behaviorally-identical mutant is, by construction, one the reward would treat as correctly accepted, so the objective cannot express design conformance at all." `affects_works`=["[UTRL, OpenReview:VqjNYF9nbP]"]. `limitation_type`="theoretical".
- L3: "Defect-focused review reframes evaluation around *key bug detection*, still a functional-defect target; it does not model naming/layering/cross-cutting conventions as a separate category of thing that could be missed, nor measure them via the test suite." `affects_works`=["[DefectFocusedReview, OpenReview:mEV0nvHcK3]"]. `limitation_type`="generalizability".
- L4: "That VERINA needs formal specifications and proofs *in addition to* a test suite to pin down intended behavior is indirect evidence that tests under-express properties — but it treats this as a benchmarking-scope choice, not as a measured account of *which* property classes tests structurally cannot reach." `affects_works`=["[VERINA, OpenReview:0A4Uf88pog]"]. `limitation_type`="theoretical".
- L5: "Execution-grounded benchmark construction deliberately equates 'correct' with 'passes the derived functional tests'; the entire pipeline is built to make functional-correctness the oracle, and so cannot, and does not attempt to, surface design properties orthogonal to input/output behavior." `affects_works`=["[AutoCodeBench, OpenReview:fN0MED2Idq]"]. `limitation_type`="generalizability".
- L6: "The self-referential-MAS work names the code-and-tests-hallucinate-together problem but resolves it only by adding more agents/verification in the same LLM loop; it provides no *test-suite-independent* oracle of the kind required to certify that a mutant genuinely violates a convention rather than merely going unnoticed." `affects_works`=["[SelfRefMAS, OpenReview:Cug26Y0RlT]"]. `limitation_type`="theoretical".

- **C1**: "Distinguishing a mutant that is 'functionally equivalent yet design-violating' from a mutant that is merely equivalent requires an authoritative, test-suite-independent oracle for the design convention itself — without one, 'the suite didn't kill it' and 'the convention wasn't actually violated' are indistinguishable." `source`="inferred".
- **C2**: "Cross-cutting concerns and layering/naming conventions are frequently non-local (spanning multiple call sites, modules, or whole-codebase structure); standard mutation operators perturb a single local statement, so constructing a mutation that violates a non-local convention while remaining a minimal, functionally-equivalent change is not straightforward." `source`="inferred".
- **C3**: "Temporal/ordering properties are properties of an execution trace, not of a single input/output pair; mutation *killing* is classically defined as 'produces different final output,' which does not naturally capture 'produces the same final output via a different, convention-violating event ordering.'" `source`="inferred".

## N6 — Methodology

**[HYPOTHESIS]** — extrapolated from the one-sentence minimal experiment, made operational (what is measured/built, with what instrument, at what granularity).

### `overview` **[HYPOTHESIS]**
"The method builds a *design-mutation* pipeline layered on a standard mutation-testing engine. For each of three constraint categories (naming/identifier, layering/cross-cutting boundaries, temporal/ordering), it (i) generates candidate mutants with category-specific operators, (ii) certifies each candidate is functionally equivalent to the original independently of the test suite under study, (iii) independently labels each candidate as a genuine convention violation via a rule-based checker, then (iv) runs the existing, unmodified test suite against the surviving labeled mutant set and records kill/survive per category, aggregated into a blind-spot profile and contrasted with the same suite's ordinary functional mutation score. **Staged plan.** *Pilot (= seed's minimal experiment):* on 1–2 well-instrumented open-source Java projects with mature JUnit suites, run the full pipeline for all three categories and report per-category survival vs. functional mutation score — enough to establish existence of a blind spot. *Scale-up:* extend to ~10–15 subject systems across two ecosystems (Java + Python), add a stronger LLM-generated-test baseline, and test whether the per-category ordering of survival rates is stable across systems."

### `key_components`
- **M1** — "Design-constraint taxonomy & mutation-operator catalog": three constraint classes each paired with an operator that violates it while preserving behavior. *Naming*: rename-only refactorings that break a documented identifier convention (e.g. rename a `*Factory` class to a non-conforming name, propagate references — behavior-identical, Checkstyle-visible). *Layering/cross-cutting*: relocate a call or dependency so a layering rule is broken (e.g. UI-layer method calls a persistence class directly) with an equivalent call graph — ArchUnit-visible. *Temporal/ordering*: reorder two commutative-on-output but convention-ordered operations (e.g. `validate(); log();` → `log(); validate();`) so final output is unchanged but the required event order is violated — trace-checker-visible. Granularity: one operator application = one mutant, tagged with category and the specific rule violated.
- **M2** — "Functional-equivalence verifier": certifies behavioral equivalence *independently of the suite under study*, via (a) differential execution on a large auto-generated input corpus (e.g. EvoSuite/randoop-generated or fuzzed inputs disjoint from the subject suite) comparing observable outputs, plus (b) bytecode/AST-diff sanity checks for rename-only mutants. A mutant is admitted only if no differential input distinguishes it. Granularity: per-mutant admit/reject.
- **M3** — "Independent convention-violation checker": the test-suite-independent ground truth demanded by C1 — Checkstyle (naming rules), ArchUnit (layering/cross-cutting boundary rules), and a lightweight aspect/bytecode-instrumentation trace monitor (temporal order). Each certifies a mutant genuinely violates its target rule. Granularity: per-mutant violates/does-not-violate, per rule; a stratified sample is manually audited (see N8 metrics).
- **M4** — "Kill-rate measurement harness": drives the standard mutation engine (PIT/pitest for Java, mutmut for Python) in a mode where the *mutant set is supplied by M1–M3* rather than the engine's default operators, runs the unmodified subject suite, and records kill vs. survive. For temporal mutants the kill criterion is extended: a mutant counts as killed if any test fails on it, including trace-order assertions. Granularity: per-mutant verdict, aggregated per category and per subject system.
- **M5** — "Blind-spot profile aggregator": summarizes M4 verdicts into per-category survival rates with confidence intervals, and computes the contrast against the same suite's functional mutation score (PIT default operators). Output: the structural account — which categories are almost never caught (a blind spot) vs. incidentally caught (e.g. a naming mutant killed only because a test asserts a literal identifier string).

- **Compute/effort, order of magnitude.** CPU-bound, no GPU required for the core measurement.
