## Abstract

Multi-step agent benchmarks and reward signals routinely grade long-horizon tasks by checking each intermediate milestone independently — a file exists, a database row appears, a tool call returns the right signature — because verifying full end-to-end correctness directly is expensive. Recent audits have shown that *whole-task outcome* verifiers in agent benchmarks can be defeated at scale, and that unprompted agents already exploit verifiers in a measurable fraction of rollouts; what those audits leave unexamined is this practice's structural core at the *milestone* level: a milestone verifier certifies a local, observable signal, but the prerequisite state that signal is supposed to imply is a property of causal history, and the map from history to signal is many-to-one. Many trajectories that never establish a milestone's true prerequisite state can still produce the same passing signal, so satisfying every checkpoint is strictly weaker than establishing what those checkpoints jointly certify. We build a multi-step agent task suite annotated with an explicit prerequisite dependency graph, equip each milestone with a verifier whose local-only scope is directly auditable in code, and score every trajectory against a separate terminal state-consistency oracle sharing no logic with the verifiers. Our headline estimand is the *natural incidence* of checkpoint bypass in unprompted rollouts of real LLM agents; a constructed suite of out-of-order, step-skipping, and direct-injection trajectories serves as a constructibility gate and lets us characterize which strategies and graph topologies admit bypass at all, rather than being reported as a deployment incidence itself. A strongest-checker control isolates whether any observed bypass reflects structural locality rather than weak checker implementations, and a manual audit bounds the terminal oracle's own error before any rate is attributed to genuine bypass. Because trajectories are nested within tasks, every rate is reported with task-clustered (not trajectory-i.i.d.) intervals. We report the resulting checkpoint-bypass rates — natural incidence, by strategy, and by graph topology — and what they imply for milestone-based grading in agent evaluation and training.

## Introduction

Long-horizon agent tasks are rarely graded end to end. A coding agent that must edit a file, run a migration, and update a config is instead checked milestone by milestone: does the file exist, did the test pass, does the database row match. This decomposition is not a shortcut taken reluctantly — it is standard practice across agent benchmarks and training pipelines, because directly verifying whether the entire multi-step task actually succeeded is often expensive or underspecified, while each individual milestone typically has a cheap, well-defined local check; recent systems make the practice explicit, grading agents on verifiable milestone DAGs reconstructed from commit histories [SWEMilestone2026] and anchoring RL training rewards to dynamically distilled milestones [AdaptiveMilestoneReward2026]. The appeal is obvious: if every milestone's checker passes, the reasoning goes, the task must have been completed correctly.

That verifiers in agent settings can be gamed is, by mid-2026, no longer news: a recent audit found 16% of 1,968 tasks across five terminal-agent benchmarks hackable by frontier models attacking the task's *outcome verifier* [HackerFixerLoops2026], and an ultra-long-horizon benchmark observed unprompted reward-hacking behavior in 13.8% of real-agent rollouts [SWEMarathon2026]. But both of these measure the whole-task outcome check as a single attack surface. What still has not been directly measured is the reasoning that milestone decomposition quietly adds on top: that passing *every* milestone checker is *sufficient* evidence that the task's true prerequisite structure was actually respected. A milestone verifier can only observe its own local signal — a file's presence, a row's content, an assertion's outcome — and that signal is a many-to-one projection of the causal history that produced it. Many different histories, including ones that never executed the milestone's real prerequisite step, can produce an identical passing signal. A trajectory that completes milestones out of order, skips a step whose effect it fakes another way, or simply writes the expected file or database row directly, can in principle satisfy every local checker without ever establishing what those checkpoints are supposed to jointly certify. If this is possible in practice and not just in principle, then benchmark scores, training reward signals, and "task complete" judgments built on milestone-by-milestone grading may be systematically overstating real multi-step competence — and the verifier itself, rather than the task, becomes what gets gamed.

The closest existing work approaches this concern from adjacent angles without closing it. The verifier-gaming measurement line just cited is nearest in spirit: it establishes that outcome verifiers are exploitable at scale [HackerFixerLoops2026], that exploitation can be made deterministically measurable by embedding hackable opportunities into environments by design [HackVerifiableEnvs2026], and that it occurs unprompted [SWEMarathon2026] — but in every case the object attacked is a single per-task outcome check, so none of these can ask whether a *set* of milestone-scoped checkers over an explicit prerequisite graph can all pass while the end-to-end state is inconsistent, nor attribute any such gap to checker locality rather than checker weakness. Evaluation frameworks that catalog how agent benchmarks actually grade tasks — file and existence checks, tool-signature checks, database-state comparisons, exact-match assertions — argue convincingly that this local grading under-measures the interaction *process*, but their remedy is a more holistic judge over the full trajectory, not a measurement of how often local checks can be satisfied while the true prerequisite state never holds. Work that builds agents around explicit prerequisite dependency graphs treats the graph as a planning aid for producing valid action sequences, correcting it from feedback when a plan fails — but never asks the dual question of whether an independent milestone verifier can be satisfied while the graph's prerequisites are unmet. Elsewhere, process reward models that score reasoning steps independently are already known to be locally plausible yet globally inconsistent — a step that looks fine on its own can become invalid once the full solution is assembled — but this observation has so far been made for linear reasoning chains graded against a single final answer, not for multi-milestone agent trajectories with an explicit dependency structure and adversarial completion strategies. And checklist-based process reward models for web agents have shown that template-matching checkers can be satisfied by superficial compatibility rather than genuine task progress — direct evidence that surface-level checking is exploitable, but not a measurement of how often, or under which conditions, that exploitation actually produces a checkpoint pass alongside true task failure.

Turning this gap into something measurable surfaces its own difficulties. The space of ways a trajectory could reorder, skip, or inject its way past a set of milestones grows far faster than the number of milestones, so no finite constructed suite can exhaustively cover it — any reported rate is necessarily a sample, and has to be reported as a lower bound rather than a population-level number. Locality itself has to be established as a real, auditable property of the verifier code, not merely assumed, or any measured gap between milestone success and true task success could just as easily be an accident of a specific implementation. Among the three bypass strategies, direct state injection is the sharpest test of this locality: it forges a milestone's local success signal without needing an executable path through the actual task logic, and distinguishing a state that was legitimately produced by executing prior steps from one whose surface signature was simply written in place requires authenticating causal history — something a lightweight, milestone-scoped checker cannot do without becoming as expensive as full state tracing. And because any measured bypass could, in principle, be an artifact of this study's own checkers being weaker than what a careful benchmark designer would actually deploy, the finding is only informative if it survives being tested against the strongest realistic local checker available, not just a convenient toy one. Finally, the terminal ground truth used to detect a bypass is itself a nontrivial specification — a buggy oracle would manufacture false inconsistencies that masquerade as bypasses, or a lenient one would hide real ones.

Our approach turns each of these obstacles into a specific design decision. Task generation is stratified across prerequisite-chain depth and branching factor and across all three bypass-strategy families, so that any reported bypass rate can be decomposed by exactly the structural axes that determine where bypass concentrates, rather than presented as one undifferentiated number. Every per-milestone verifier is built with a statically auditable scope restriction — no code path reads another milestone's provenance — so that locality is a checkable property of the instrument, not an assumption about it. A dedicated injection-strategy probe holds a milestone's surface signature fixed while varying only whether its true prerequisite was executed, directly testing whether state injection defeats local checking as sharply as its logic predicts. A strongest-local-checker control replaces every verifier with the richest realistic check per checker type, still scoped to its own milestone, to test whether any bypass survives against the best a real system would plausibly deploy — separating a structural finding from an artifact of weak instrumentation. And the terminal state-consistency oracle is validated on its own terms: a manual audit of its verdicts on trajectories known to be honest bounds its false-inconsistency rate before any bypass claim is reported. In its evidence shape, this is deliberately a controlled measurement study that directly tests an assumed-sufficient claim — the mold of close empirical examinations such as the calibration analysis of pre-trained language models [PLMCalibrationCloseLook2023] — rather than a proposal for a competing verification method.

We evaluate this design on multi-step tasks spanning coding and filesystem operations, database and tool-use state, and web-page state, comparing constructed adversarial trajectories against honest, topologically-valid completions and against the strongest-checker control, and separately measuring how often real LLM agents produce a milestone-complete-but-inconsistent rollout without any adversarial intent — this natural-incidence question is the paper's headline estimand; the constructed trajectories answer a different, prior question (can bypass be built at all, and which strategies and topologies admit it) and are never pooled with the natural-incidence rate.

In summary, we contribute:
- A formalization of the asymmetry between what a per-milestone verifier can observe and what it is meant to certify: milestone checking is a many-to-one projection of causal history onto a local signal, so satisfying every checkpoint is strictly weaker than establishing the prerequisite state those checkpoints jointly imply.
- A constructed multi-step agent task suite with explicit prerequisite dependency graphs, auditably locality-scoped per-milestone verifiers mirroring standard benchmark grading, and a terminal state-consistency oracle held disjoint from and validated independently of those verifiers.
- A strongest-checker attribution control that isolates whether observed bypass reflects the structural fact of milestone-scoped checking, rather than merely weak or lazy checker implementations — together with an oracle-validity audit that bounds the ground truth's own error before any bypass rate is reported.
- A headline measurement of the *natural* checkpoint-bypass incidence in unprompted rollouts of real LLM agents, together with a secondary constructibility characterization — by bypass strategy and by dependency-graph topology — of the researcher-constructed trajectory space, with every rate reported under task-clustered (not trajectory-independent) uncertainty, and what both imply for milestone-based grading in agent benchmarks and reward design.

## Problem Definition

**Formal setup.** Consider a multi-step task `T = (Σ, V, E, Φ, Ω)`: a state space `Σ`; a milestone set `V = {v_1, ..., v_n}`; a prerequisite dependency graph `E ⊆ V × V`; a set of per-milestone verifiers `Φ = {φ_k}`; and a terminal oracle `Ω`. A trajectory `τ = (a_1, ..., a_m)` is an action sequence inducing a state path with terminal state `σ_τ`. Each verifier `φ_k: view_k(τ) → {0,1}` is restricted to milestone `v_k`'s own local signal — it has no read access to any other milestone's provenance — and the all-pass indicator is `A(τ) := ⋀_k φ_k(τ)`. The oracle `Ω: σ_τ → {0,1}` is a total function comparing the trajectory's terminal state to the task's canonical goal state, sharing no code or logic with any `φ_k`. A **bypass event** is `B(τ) := A(τ)=1 ∧ Ω(τ)=0`: every milestone verifier passes, yet the terminal state is inconsistent with the goal. The **checkpoint-bypass rate** is defined conditionally, `ρ := P_{τ∼D}[Ω(τ)=0 \mid A(τ)=1]`, over a pre-registered trajectory distribution `D`, and is instantiated as **two distinct, never-pooled quantities**: the **headline** natural incidence `ρ_nat` over the distribution `D_nat` of real-agent rollouts (the reference population is rollouts a working milestone-verification pipeline would score complete; this is the quantity that bears on whether deployed per-milestone verification can be trusted without a separate terminal check), and the **secondary** constructed-suite rate `ρ_c` over the researcher-authored distribution `D_c` of adversarially built traces. Because `D_c` is designed by construction to drive `A(τ)=1` while `Ω(τ)=0` for the injection family, `ρ_c` is an existence/constructibility quantity, not an incidence estimate of any deployed population — it characterizes *which strategies and topologies admit bypass*, and is reported as a manipulation-check gate rather than a headline finding.

**Why this is hard.** The bypass space grows combinatorially in the number of milestones — reorderings, skip-patterns, and injection points over a dependency graph — so any finite constructed sample can only characterize where bypass concentrates along structural axes such as prerequisite-chain depth and node in-degree, not certify an exhaustive or worst-case rate. Locality itself is not free to assume: `φ_k`'s restriction to `view_k(τ)` has to be an auditable property of the verifier's code, since a claim about the consequence of milestone-scoped checking is only meaningful if that scoping is genuinely enforced rather than incidentally present. Among bypass mechanisms, direct state injection poses a distinctive difficulty: distinguishing a state produced by legitimately executing `v_k`'s prerequisites from one whose surface signature was written in place requires authenticating causal history, which a verifier confined to `view_k(τ)` cannot do without effectively becoming a full state tracer. A measured `ρ > 0` is also not on its own evidence that milestone-scoped checking is structurally insufficient, rather than merely evidence that this study's specific verifier implementations were weak — ruling out the latter requires testing against the strongest realistic, still milestone-scoped checker available. And `Ω` itself is a nontrivial specification: since it must independently reconstruct and compare against a canonical goal state, its own false-inconsistency rate on trajectories known to be honest has to be bounded before any `B(τ)` count is attributed to genuine bypass rather than oracle error.

## Method Overview

At a conceptual level, this is a single measurement pipeline with five cooperating parts, applied to both adversarially constructed trajectories and to natural rollouts of real agents. Multi-step tasks are generated with an explicit prerequisite dependency graph and stratified across topology and bypass-strategy families; each milestone receives a verifier whose local-only scope is a checkable code property rather than an assumption; a dedicated injection probe and a strongest-checker control jointly test whether any measured gap between milestone success and true task success is a genuine consequence of that locality — and specifically of state injection — rather than an artifact of weak instrumentation; and a terminal oracle, held disjoint from every verifier, is itself audited before its verdicts are trusted as ground truth.

The **topology-stratified bypass sampler** parameterizes task generation over prerequisite-chain depth and branching factor and constructs reorder, skip, and injection trajectories across these strata, so the resulting bypass rate can be decomposed by exactly the structural features that plausibly drive it, rather than reported as a single undifferentiated number. The **locality-scoped verifier suite** implements each milestone's checker with a statically auditable restriction to that milestone's own local signal, mirroring the checker types real agent benchmarks use, and is the instrument applied to both constructed trajectories and real-agent rollouts to produce the constructed and natural bypass rates respectively. The **injection provenance probe** isolates the state-injection strategy specifically, holding a milestone's surface signature fixed while varying whether its true prerequisite was executed, to test whether injection defeats locality more sharply than reordering or skipping. The **strongest-checker attribution control** reruns the same measurement with the richest realistic, still milestone-scoped, checker per type, to test whether any bypass survives against the best real systems would plausibly deploy. And the **disjoint oracle with audit** validates the terminal ground truth itself, via a manual review of its verdicts on trajectories already known to be honest, before any bypass count is reported as evidence.

## Methodology

### Topology-Stratified Bypass Sampling

**Challenge.** The bypass space — reorderings, skip-patterns, and injection points over an arbitrary prerequisite graph — grows far faster than the number of milestones, so no finite constructed suite can exhaustively cover it, and an unstructured convenience sample gives no way to characterize where bypass concentrates or bound the direction of undercoverage.

**Insight.** Exhaustive coverage is impossible, but a *stratified*, not exhaustive, sample — organized along the structural axes (chain depth, branching factor) and strategy families most likely to determine where bypass concentrates — turns "we cannot cover everything" into "we can characterize where it concentrates and report the rate as an explicit, structured lower bound."

**Method.** Task generation is parameterized over prerequisite-chain depth and node in-degree, and bypass trajectories are constructed across all three strategy families (reorder, skip, inject) within each topology stratum. The resulting checkpoint-bypass rate is always reported alongside its stratification — never as a single pooled figure — and explicitly labeled as a lower bound over the sampled distribution.

### Locality-Scoped Verifier Suite

**Challenge.** A milestone verifier's job is to certify that milestone's prerequisite state, but if its scope restriction to that milestone's own local signal is merely assumed rather than enforced, any measured gap between milestone success and true task success could be an accident of one particular implementation rather than a consequence of milestone-scoped checking in general.

**Insight.** Locality has to be built into the verifier as a statically checkable code property — no path reads another milestone's provenance — so that it can be audited directly, and so that the same instrument can be pointed at two different trajectory distributions (adversarially constructed traces and natural agent rollouts) to produce two independently interpretable readings from one measurement design.

**Method.** Each milestone's verifier is implemented as a sandboxed check restricted to that milestone's own local signal — file/existence checks, pattern or regex matches, unit sub-tests, tool-signature checks, database-state comparisons, and exact-match assertions, mirroring the mechanisms real agent benchmarks use — with the scope restriction confirmed by a code-dependency audit before any rate is computed. The same verifier suite and disjoint terminal oracle are applied first to adversarially constructed trajectories, yielding the constructed checkpoint-bypass rate, and separately to unprompted rollouts of real LLM agents scored complete by the verifiers, yielding the natural bypass incidence.

### Injection Provenance Probe

**Challenge.** Among the three bypass strategies, state injection is the one hardest to rule out in principle: it can forge a milestone's exact local success signal without needing to approximate any real control-flow path through the task, and distinguishing a legitimately produced prerequisite state from a directly written surface signature is, for a lightweight checker, effectively as hard as full causal-history tracing.

**Insight.** If injection is genuinely the sharpest bypass mechanism, holding a milestone's surface signature exactly fixed while varying only whether the real prerequisite operation was executed should isolate that mechanism cleanly, separate from any confound with the trajectory's overall plausibility as an executable action sequence.

**Method.** Within the injection-strategy trace family, each milestone's expected local artifact (the expected file, pattern, or database row) is written directly without executing the underlying prerequisite operation, and the resulting per-milestone verifier verdicts and bypass rate are compared against the reordering and step-skipping strategy families constructed over the same tasks.

### Strongest-Checker Attribution Control

**Challenge.** Any measured bypass is only informative about milestone-scoped checking in general if it is not simply an artifact of this study's own verifier implementations being weaker or lazier than what a careful benchmark designer would realistically deploy — otherwise the finding reduces to "these particular toy checkers were easy to fool," a much less interesting claim.

**Insight.** Replacing each verifier with the richest realistic check of its type — while preserving milestone-scoping by construction, so locality itself is never relaxed — is the only way to test whether bypass survives against the strongest plausible real-world instrumentation, isolating structural locality from implementation weakness.

**Method.** Each per-milestone verifier is replaced by the fullest realistic local check of its checker type (the deepest unit sub-test, the strictest exact-match, the fullest database-state comparison), matched in capability and compute cost to the standard suite, while remaining scoped to its own milestone with no added cross-milestone visibility. The injection-strategy bypass rate is recomputed against this control and compared to its value under the standard verifier suite.

### Disjoint Oracle with Audit

**Challenge.** A terminal oracle capable of detecting when milestone-level success does not imply true task success requires its own global specification of task state, which can be as difficult to get right as the original task's success criterion — a buggy oracle would manufacture false inconsistencies that masquerade as bypasses, while an overly lenient one would hide genuine ones.

**Insight.** An oracle's trustworthiness is itself measurable, not merely assumable: trajectories that are known, by construction, to have honestly executed every prerequisite give a case where the "correct" verdict is known independently of the oracle, making them the right instrument for bounding the oracle's own error before its verdicts are trusted as ground truth for anything else.

**Method.** The terminal oracle is implemented as a total function of final task state — a filesystem hash-set, a database row-set, or deterministic program output — sharing no code or logic with any per-milestone verifier, confirmed by a code-dependency audit. A stratified sample of the oracle's verdicts on honest, topologically-valid trajectories is manually reviewed to measure its false-inconsistency rate, which is reported as an explicit bound on measurement error before any bypass rate involving that oracle is presented as evidence.

## Experiments

### Experimental Setup

**Datasets.** A constructed prerequisite-DAG agent task suite is the primary evaluation object: a hand-authored pilot set (coding and filesystem tasks, roughly 5–12 milestones per task, graded by file hashes and deterministic program output) establishes a canonical, independently computable terminal state cheaply, and a procedurally generated scale-up set extends coverage to tool-use/database-state and web-action domains. Real-world task substrates whose grading practice this suite's verifiers are built to mirror — SWE-bench-style repository tasks, tool-use benchmarks with database-state, tool-selection, and tool-signature grading [MCPAgentBenchToolUse2026; RLVRAtlassianToolUseAgents2026], and function-calling leaderboards — are used to justify that the constructed verifiers reflect standard, not idealized, agent-benchmark grading. Web-action tasks in the style of existing web-agent benchmarks are included specifically to test whether the topology-bypass relationship generalizes to a domain whose per-milestone checks are page/DOM-state comparisons rather than file, database, or tool-signature checks.

**Baselines** (sanity-check and attribution comparators, not competitors to beat — this is a measurement study, and no research question here is framed as "our procedure beats baseline X"). An honest-trajectory control — topologically valid completions that genuinely execute every prerequisite — is expected to produce a near-zero bypass rate; it is the necessary check that the verifier suite and the oracle agree on legitimate completions, so that any positive rate on constructed adversarial trajectories is attributable to the bypass mechanism rather than to baseline disagreement between the two measurement instruments. A strongest-local-checker control, described above as its own methodology module, tests whether bypass survives against the best realistic instrumentation rather than only against this study's standard checkers.

**Metrics.** The checkpoint-bypass rate reported for two distinct, never-pooled quantities — the natural incidence `ρ_nat` (headline) and the constructed-suite rate `ρ_c` (constructibility gate) — broken down by bypass strategy and by graph-topology stratum; the odds ratio of bypass on prerequisite-chain depth and node in-degree from a mixed-effects logistic regression; and the oracle's own false-inconsistency rate from manual audit. Per-checker-type breakdowns are reported descriptively only — the design pre-registers no inferential claim about which checker types are vulnerable (A3 is a continuous reporting discipline, not a hypothesis), an acknowledged scope restriction.

**Dependence structure (analysis-plan note).** Constructed trajectories are nested within tasks (roughly 5–15 traces per task share the same DAG, verifier code, and oracle), so no test below treats trajectories as independent draws. Rate intervals (RQ1, RQ2) use a task-level cluster bootstrap (10,000 resamples of tasks with replacement, percentile interval); strategy contrasts (RQ4) and the strongest-checker attribution ratio (RQ5) use cluster-robust (task-level) standard errors, equivalent to a GEE binomial model with exchangeable working correlation; the topology model (RQ3) is a mixed-effects logistic regression with a task-level random intercept. Every rate is reported with the number of distinct tasks (`n_tasks`) alongside the number of trajectories, since `n_tasks` is the effective sample size under clustering, not `n_trajectories`.

**Research questions:**
1. RQ1 — Can checkpoint bypass be constructed at all (a constructibility gate, not the headline finding)?
2. RQ2 — Do real agents produce checkpoint-complete-but-inconsistent rollouts without adversarial intent? **(headline)**
3. RQ3 — Does dependency-graph topology modulate the bypass rate?
4. RQ4 — Which bypass strategy is most effective at defeating milestone verification?
5. RQ5 — Is any observed bypass attributable to structural locality rather than weak checker implementations?
6. RQ6 — Is the terminal oracle itself valid ground truth?

#### RQ1: Can checkpoint bypass be constructed at all? (constructibility gate)

**Role.** RQ1 is a manipulation check, not a headline claim: because the injection strategy is defined to write the exact surface signature the milestone verifiers check, a pass is expected by construction. A pass licenses RQ3–RQ5 (which strategies/topologies admit bypass, and whether it survives stronger checkers) and the existence reading of Claim 1 ("bypass is constructible"); it is never read as evidence about deployed incidence — that question belongs to RQ2. A failure here would be the more informative and surprising outcome.

**Setup.** On the pilot DAG suite, construct at least 300 trajectories (20–40 tasks × reorder/skip/inject × roughly 5 variants each) and compute the constructed-suite bypass rate `ρ̂_c` as the fraction passing every milestone verifier while failing the terminal oracle. Task-level cluster bootstrap (10,000 resamples, percentile interval) in place of a trajectory-i.i.d. binomial/Wilson interval.

**Expected outcome.** `ρ̂_c ≥ 0.10` with the cluster-bootstrap 95% lower bound above 0.05 — demonstrating bypass is constructible on this suite, gating the strategy/topology/attribution analyses below.

**Falsification condition.** Refuted if the cluster-bootstrap 95% lower bound on `ρ̂_c` does not exceed 0.05 — that would mean constructed bypass trajectories cannot reliably defeat milestone verification on this suite even by design, an unexpected and highly informative failure (see the RQ1 fallback in `paper.md`).

**Hypothesis (plain language).** Milestone checkpoints can, in practice and not merely in principle, all be satisfied while the task's true prerequisite structure is never established — a constructibility result, not yet a claim about deployed agents.

**Metrics.** Constructed-suite bypass rate `ρ̂_c` with task-level cluster-bootstrap 95% CI and `n_tasks`; per-checker-type breakdown.

#### RQ2: Do real agents produce checkpoint-complete-but-inconsistent rollouts without adversarial intent? (headline)

**Role.** This is the paper's headline hypothesis: the reference population is rollouts a working milestone-verification pipeline would already score complete, so `ρ_nat` bears directly on whether deployed per-milestone verification can be trusted without a separate terminal check — unlike RQ1's researcher-authored constructed rate. The named nearest precedent is `SWEMarathon2026` [SWEMarathon2026]'s 13.8% unprompted reward-hacking incidence; `ρ_nat` is not comparable to that number by construction — theirs counts detected exploit *attempts* over all rollouts, ours counts terminal-state inconsistency *conditional on* the rollout being scored milestone-complete, net of the audited oracle error (RQ6) — and this estimand difference, not the existence of unprompted gaming, is what RQ2 contributes.

**Setup.** Among rollouts of 3–5 real LLM agents (at least 3 seeds each, spanning at least 20 distinct tasks) on the scale-up suite that are scored complete by the milestone verifier suite, measure the fraction that fail the terminal oracle, net of the audited oracle false-inconsistency rate (RQ6). Task-level cluster-bootstrap 95% CI on `ρ̂_nat`, and a cluster-robust two-proportion comparison against `ρ̂_c` from RQ1, over at least 200 verifier-complete rollouts. *Completion-yield rule (pre-registered in `experiment_design.md`):* the ≥200 floor counts *verifier-complete* rollouts, not rollouts attempted, so the total rollout budget scales as 200 divided by the observed milestone-completion yield of the chosen agents on the scale-up tasks — the walking-skeleton/pilot measures that yield first, gate PG-3 blocks H4 scoring until the 200-complete/≥20-task floor is met, and if the measured yield implies an infeasible total budget the task mix is re-selected under PG-0 rather than the floor being lowered. No yield value is assumed in advance.

**Decision rule (power-corrected).** `H4` holds iff `ρ̂_nat ≥ 0.01` (≥2 bypass events at n=200) with the cluster-bootstrap 95% lower bound above 0. The decision threshold (0.01) is deliberately set *below* the pre-registered effect floor (`ρ_nat ≥ 0.02`, the smallest incidence considered deployment-relevant) because setting the threshold equal to the floor caps power at ≈0.57 regardless of `n`; decoupling them gives power `P(X≥2 \mid \mathrm{Bin}(200,0.02)) ≈ 0.91` at the floor. Pre-declared edge cases: `ρ̂_nat = 0` → FAIL (invoke the RQ2 fallback); `0 < ρ̂_nat < 0.01` → INCONCLUSIVE-at-n (report the required n), never reported as a null result.

**Expected outcome.** Natural incidence clears the decision rule above and is significantly lower than the constructed-suite rate — bypass occurs during ordinary operation, but less often than under deliberate construction.

**Falsification condition.** Refuted (FAIL) if `ρ̂_nat = 0`; INCONCLUSIVE-at-n if `0 < ρ̂_nat < 0.01`. Either non-PASS outcome means bypass is not shown to already occur, unprompted, in ordinary agent operation at the pre-registered floor.

**Hypothesis (plain language).** Checkpoint bypass is not purely a constructed vulnerability; it already occurs, at a lower but nonzero rate, in agents that were never instructed to exploit the verification scheme.

**Metrics.** Natural bypass incidence `ρ̂_nat` with task-level cluster-bootstrap 95% CI and `n_tasks`; cluster-robust two-proportion comparison against `ρ̂_c`.

#### RQ3: Does dependency-graph topology modulate the bypass rate?

**Setup.** Over the scale-up suite (at least 200 tasks), fit a **mixed-effects logistic regression** of the per-trajectory bypass outcome on prerequisite-chain depth and node in-degree, with a **task-level random intercept** (trajectories are nested in tasks; see the dependence-structure note above). Wald tests on the fixed-effect coefficients, Holm-corrected across the two predictors, α = 0.05.

**Expected outcome.** At least one fixed-effect coefficient shows an odds ratio greater than 1.2 per unit, with a significant Wald test — deeper or higher-fan-in prerequisite structure raises the odds of bypass.

**Falsification condition.** Refuted if neither predictor's odds ratio exceeds 1.2 with a Holm-corrected significant Wald test — that would mean bypass risk is not modulated by prerequisite-chain depth or node in-degree, i.e., graph topology does not predict where bypass concentrates.

**Hypothesis (plain language).** The risk of checkpoint bypass is not uniform across task structures; it is amplified by more complex prerequisite graphs, which give a locality-scoped verifier more unseen prior state to be decoupled from.

**Metrics.** Odds ratio per unit depth and per unit in-degree (mixed-effects logistic regression, task random intercept), with confidence intervals and Wald test statistics; `n_tasks` and per-cell trajectory counts.

## Related Work

The closest prior work to this paper spans three groups: a **verifier-gaming measurement group** of 2026 arXiv works (verified by ID against the arXiv API, 2026-08-15) that are now the nearest neighbors overall and that this paper concedes to and positions against first; a **verified-cache group** of three method-twins (`CodeReproducibilityGap2025` [CodeReproducibilityGap2025], `RevealWeakestLink2024` [RevealWeakestLink2024], `MATPLogicalFlaws2025` [MATPLogicalFlaws2025]) that are `selected` cache records with resolvable digests; and a **disjoint-corpus group** (TED, XENON, Gistify, StepORLM, LatentVeracity, WebArbiter, GTool, DiffTaskGraph) surfaced by an early keyword search but **absent from this topic's verified reference cache** — retained below only as named future harvest targets, per `digest.md`'s 2026-07-04 cache-integrity note, and not load-bearing for any claim in this paper.

**Verifier-gaming measured at scale (2026, arXiv-verified).** `HackerFixerLoops2026` [HackerFixerLoops2026] is the nearest neighbor to this paper's motivating claim: it audits 1,968 tasks across five terminal-agent benchmarks, finds 16% hackable by frontier models attacking the task's outcome verifier, and proposes an adversarial hacker–fixer loop that patches verifiers until known exploits fail. We concede outright that verifier exploitability in agent benchmarks is therefore already directly measured — the gap this paper claims is strictly narrower and different in kind: their unit is a single whole-task outcome verifier and their estimand is attack success given the task description, whereas ours is the conditional rate at which *every* milestone-scoped verifier over an explicit prerequisite DAG passes while a disjoint, independently audited terminal-state oracle fails, decomposed by bypass strategy and graph topology, with a strongest-checker control attributing any gap to checker *locality* rather than checker *weakness* — an attribution question their fixer loop's own success (driving attack rates to zero by patching implementations) sharpens but does not answer. `SWEMarathon2026` [SWEMarathon2026] supplies the natural-incidence precedent: 13.8% of unprompted real-agent rollouts on ultra-long-horizon software tasks exhibit reward-hacking behavior detected by adversarial review of test suites and environments. We concede that unprompted verifier exploitation is thereby established as a live phenomenon; our headline `ρ_nat` differs operationally — it is conditioned on rollouts a milestone-verification pipeline would already score complete, scored against a terminal state-consistency oracle rather than by detecting exploit *attempts*, and reported net of an audited oracle false-inconsistency rate — so the two numbers answer different questions (how often agents try to game a grader vs. how often milestone-complete rollouts are terminally inconsistent). `HackVerifiableEnvs2026` [HackVerifiableEnvs2026] pioneers the constructed-arm paradigm this paper's RQ1 also uses — embedding detectable exploitation opportunities into environments so exploitation is verifiable by design — in TextArena game environments with a single evaluation signal per environment; our constructed suite transplants that design move to multi-milestone, prerequisite-structured agent tasks where the object of study is the checker *set*, not one signal. Finally, `SWEMilestone2026` [SWEMilestone2026] and `AdaptiveMilestoneReward2026` [AdaptiveMilestoneReward2026] document that milestone-DAG grading and milestone-anchored RL rewards are now deployed practice — they use milestone verification as an instrument and assume its sufficiency; this paper audits exactly that assumption. None of the five constructs locality-audited per-milestone verifiers, none defines a conditional bypass estimand against a disjoint validated terminal oracle, and none runs a locality-vs-weakness attribution control.

**Verified method-twins (cache-grounded).** `CodeReproducibilityGap2025` [CodeReproducibilityGap2025] is the nearest verified structural neighbor: it shows AI-generated code that passes a functional-correctness benchmark — the assumed-sufficient local signal — still fails a separate, disjoint reproducibility oracle built from clean-environment re-execution. We concede the shared measurement pattern (a local signal passes while a disjoint oracle fails) outright; our contribution is an explicit prerequisite DAG over milestones, *adversarially constructed* reorder/skip/inject trajectories rather than naturally produced code, milestone granularity rather than whole-program granularity, and a strongest-checker attribution control (RQ5) that isolates structural locality from implementation weakness. `RevealWeakestLink2024` (REVEAL) [RevealWeakestLink2024] introduces step-level verification of chain-of-thought reasoning specifically because final-answer correctness can mask invalid intermediate steps — the same local-versus-global verification-granularity gap this paper studies, but in the *inverse* direction (global pass masking local invalidity, rather than local pass masking global invalidity), over linear text chains rather than stateful agent trajectories with a prerequisite structure, and without a measured bypass rate under controlled adversarial strategies. `MATPLogicalFlaws2025` [MATPLogicalFlaws2025] measures a comparable gap in automated theorem proving — a correct final answer can coexist with logically invalid steps — using a disjoint theorem-prover oracle; we concede the disjoint-oracle validation pattern, and differ in operating on agent state (filesystem, database, tool-call state) rather than proof text, in treating prerequisite-state *causality* (was the state legitimately produced, i.e., provenance) as the object of study rather than logical validity of a static artifact, and in decomposing the measured rate by bypass strategy and graph topology. `RewardModelSelectionCrisis2025` [RewardModelSelectionCrisis2025] shows a Goodhart-style gap in personalized alignment: standard reward-model ranking accuracy — a locally-assumed-sufficient proxy — fails to predict true downstream behavioral alignment under reward-guided decoding. We concede this is the same assumed-sufficient-checker-vs-true-outcome asymmetry, in single-turn decoding rather than multi-step agent trajectories; our contribution is the explicit prerequisite DAG, the multi-milestone dependency structure, and the adversarially constructed (rather than naturally sampled) bypass traces. None of the four constructs an explicit prerequisite dependency graph, none adversarially constructs reorder/skip/inject trajectories, and none runs a strongest-checker attribution control — the combination this paper's design contributes.

**Agent-benchmark grading mechanisms and their remedies (disjoint-corpus, unverified — named harvest targets only).** Work cataloging how LLM-agent benchmarks are actually graded documents that evaluation is fragmented across environment-specific mechanisms — database-state comparisons, tool-signature checks, exact-match assertions — that are reliable within a single benchmark but reduce rich multi-turn interaction to a final pass/fail signal, and proposes replacing them with a holistic LLM judge scoring natural-language grading notes over the full trajectory. Checklist-based process reward models for web agents make a complementary point: template-matching checkers can be satisfied by superficial compatibility rather than genuine progress, motivating a reasoning-first, pairwise-preference alternative. And execution-faithful benchmarking work shows that repository-level coding evaluations can be passed via memorized associations or retrieval shortcuts rather than real capability, motivating a benchmark tied to observed runtime behavior instead of static artifacts. All three name real weaknesses of milestone-style or template-style checking and propose a better *checker* or grading protocol — none isolates and measures the *rate* at which currently standard, milestone-scoped checkers can all pass while a separately computed terminal ground truth fails. (These works could not be located in the verified reference cache as of this draft; the positioning above is retained as an anticipated harvest target, not a supported citation, and no claim in this paper depends on it.)

**Prerequisite-dependency planning (disjoint-corpus, unverified — named harvest targets only).** Agents built around explicit prerequisite dependency graphs — one for open-world planning, correcting an item-dependency graph from execution feedback, and one for tool selection, injecting a request-conditioned tool-dependency graph into a frozen model — both show that violating prerequisite structure produces plans that are invalid despite looking locally plausible, and that errors in an early prerequisite invalidate every descendant step. Both treat the dependency graph as a planning aid for producing or correcting valid action sequences; neither audits the dual question this paper asks: whether an independent, milestone-scoped verifier can be satisfied while the graph's prerequisites are unmet in the first place. A third line of work learns a prerequisite adjacency structure directly from observed procedural video to detect ordering mistakes online — a candidate ingredient for building a prerequisite-aware checker, but one whose detection is itself a learned forecasting signal that presumes the learned graph is correct, rather than an independent oracle over ground-truth task state. (Same cache-verification caveat as above.)

**Step-wise and process-level verifier locality (disjoint-corpus, unverified — named harvest targets only).** Process reward models that score reasoning steps independently are already documented to be myopic: a step that looks locally correct can become inconsistent once the full solution is assembled, since correctness can depend on later context the step-wise scorer never sees. A related line of work on latent veracity inference makes the same granularity point from the other direction — answer-conditioned verifiers score a whole candidate solution rather than localizing failure to individual steps. Both identify essentially the same local-versus-global tension this paper measures, but for linear reasoning or derivation chains scored against a single final answer, with no explicit prerequisite dependency graph, no adversarially constructed bypass trajectory, and no independent state-consistency oracle held disjoint from the scoring mechanism. (Same cache-verification caveat as above — retained as a harvest target, not a supported citation.)

## Conclusion

This work turns an assumption baked into standard agent-benchmark grading — that passing every milestone checkpoint is good evidence a multi-step task actually succeeded — into a measurable question with a precise identifiability structure, rather than treating milestone-based verification as self-evidently adequate. Whole-task outcome-verifier gaming is already measured at scale [HackerFixerLoops2026; SWEMarathon2026]; what this design adds is the milestone-level version of that question — whether an entire set of locality-scoped checkers over an explicit prerequisite DAG can pass while an independently validated terminal state fails, and whether that is attributable to locality itself. The central methodological wager is that a checkpoint-bypass rate is only informative once locality is built into the verifiers as an auditable property, the strongest realistic checker has been tried and still bypassed, and the terminal ground truth used to detect the gap has itself been validated against trajectories known to be honest; a weaker design risks attributing a measured rate to the wrong cause, or missing it entirely behind oracle noise. The paper's headline claim is about the *natural* incidence `ρ_nat` in unprompted real-agent rollouts (RQ2), not the researcher-constructed rate `ρ_c` (RQ1), which is a manipulation-check gate expected to pass by construction; the two are never pooled. Whichever way `ρ_nat` and the strongest-checker attribution (RQ5) land, the finding is decision-relevant either way. If natural incidence clears its pre-registered floor and survives the strongest-checker control, benchmark scores, training rewards, and deployment "task complete" judgments built on milestone checking need a companion terminal-consistency mechanism before they can be trusted at face value. If natural incidence is null or the bypass is substantially attributable to weak checker implementations (RQ5 fails), the pre-committed downgrade applies: checkpoint bypass is a constructible artifact of milestone-locality that current real-agent behavior does not exhibit unprompted and that stronger, still milestone-scoped, checkers substantially mitigate — a design caution rather than a measured deployment risk, per the paper's pre-registered global-pivot wording. Three limitations bound this claim from the outset: the constructed-suite rate is inherently a sampled lower bound over a combinatorially large bypass space, not a worst-case or population-level figure; every reported rate is computed under task-level clustering (trajectories are nested in tasks, not i.i.d.), so uncertainty intervals are wider and effective sample sizes smaller than a naive per-trajectory count would suggest; and the study is scoped to domains with a canonical, independently computable terminal state, leaving open-ended tasks without such a state for future work on oracle design.
