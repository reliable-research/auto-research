# B1.6 幻觉技能调用的注册表拦截

标签：[证据+机制]

父 Topic：B1. Verifier 充分性（agent / 代码场景）

**B1.6 幻觉技能调用的注册表拦截** [证据+机制]
> Recommending Ghosts: Registry-Grounded Gating of Hallucinated Skill/Tool Calls in Live Agent Trajectories

核心问题：LLM agent 从开放技能注册表里推荐并自动安装技能时，会产生"幻觉技能名"——这本身已被证实是可被利用的
供应链攻击前置条件（攻击者观察 agent 稳定复现的幻觉名，抢先用该名注册恶意技能，等受害者的 agent 推荐并安装）。
已发表工作的四种缓解手段全部作用于"推荐"环节（约束模型能说什么），并全部以严重牺牲可用性为代价（最好情形：
幻觉率 40.8%→3.2%，但正确技能召回率仅剩约 16%）。本 topic 问的是一个该论文未做的问题：把校验点从"推荐时"移到
"安装/执行时"，用发布者信任分级（而非单纯的"注册表里是否存在这个名字"——因为一旦被抢注，恶意技能在注册表里
同样"存在"）做门禁，能否在一个真实的多步 agent 轨迹里，既拦截被抢注的恶意安装，又不像现有四种防御那样摧毁对
合法但陌生发布者技能的可用性？拦截时机（第几步被发现）如何影响下游任务/安全结果与恢复代价？

最小实验：以 arXiv:2607.12340（《Skills That Don't Exist: A Large-Scale Study of Hallucinated Skill
Recommendation in LLM Agents》，Yuan et al.——已全文读完，非仅摘要表格）的真实测量结果为基线（36.0%–43.1% 的
幻觉率、幻觉名跨提示/跨模型可复现、自评/交叉评审仅达抛硬币水平的可检测性、四种推荐时防御无一逃过安全-可用性
的严重取舍）：构造一个"推荐→安装"决策嵌入更长任务轨迹的环境；用该论文已证实的幻觉名复现规律去生成模拟抢注者
的恶意技能名（而非任意构造）；在安装前插入一个仅依赖发布者信任分级元数据（不含任何模型判断，因为该论文已证实
模型自评是抛硬币水平）的 gate；对照"有 gate / 无 gate / 延迟 gate"三组，测量恶意安装拦截率、对"合法但未验证
发布者"技能的误拒率（与该论文自己报告的约 84%/约 55% 的召回损失直接对比）、拦截时机、以及恢复代价；真值 =
带发布者信任标注的注册表快照 + 环境执行的最终状态。

**已读完的高相似度已发表工作（结论：topic 存活，但被重新定位）**：arXiv:2607.12340 已经证实了幻觉本身、抢注
攻击可行性、检测失效、以及推荐时防御的可用性代价，并且明确未构建或测试任何安装时校验机制，只是在结尾呼吁"注册表
层面的名字保留与经过验证的推荐管线"。因此本 topic 的机制设计（安装时信任分级 gate，而非单纯存在性校验）是对
该论文自己提出但未做的下一步的具体化——剩余的开放风险不是"这个空隙是否存在"（已确认存在），而是"这个具体机制
相对于该论文结尾那句话是否足够有增量"，详见 digest.md 的 N2/N10 对此的明确讨论。
